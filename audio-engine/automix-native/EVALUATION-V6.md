# AutoMix .6：局部分轨交接验证

本轮继续参考桌面的 Java `automix` 和 C `automix-c`，改进 Twilight 自有实现；没有移植这两个项目，也没有引入受保护的研究模型。复用已验证增强包 2.2 的 Python、公开 Demucs 4.0.1 `955717e8` 模型和四声部原始缓存。播放器现在持有并打包分轨处理逻辑，无需重新下载约 2 GB 的模型包。

## 问题与行为变化

增强包原来的材料处理固定削弱人声 85%，并在每个窗口交换贝斯，无论另一首歌有没有对应声部。独唱、干净尾奏和 Natural 的短交接也会被处理；源窗口的线性进度还没有对齐原生引擎后 20% 的变速回归。

新逻辑先取得双方的真实四声部，提取 50 Hz、跨声道 RMS 曲线，再在原生输出时间轴上比较同时可听的局部人声与贝斯。只有双方声部、相对强度和实际交叉淡化增益共同支持冲突时，才平滑压低交接中的次要声部。Natural 使用较轻的处理，鼓和其他乐器不削弱。材料从原始 PCM 减去需要降低的声部；增益为 1 时逐样本保留原始 PCM，避免重建漂移。

测量单位是本地声部 RMS 振幅及导出的处理权重，不是模型概率，也不沿用参考实现的未标定服务单位。缺失覆盖、非法时间映射或非有限曲线拒绝增强；测得的静音不触发压低。阈值是本项目规则，仍需更广泛的听感与声部适合性标注。

## 所有权、缓存与回退

原始 Demucs v2 缓存键和数值执行保持兼容；新的安排不缓存旧的混合材料。双侧曲线先决定增益，再逐侧读取材料，不同时保留两份完整分轨数组。缓存关闭、无法写入或预算不足时，仅在受控材料目录暂存原始声部；成功、失败与取消均清理这些文件。第二侧写缓存时保护第一侧和待用缓存，避免在二阶段处理中提前淘汰。

宿主仍保留原生准备时间和 90 秒分轨上限；默认缓存预算仍为 512 MiB。工作进程终止确认后才释放目录与忙碌状态。材料绑定选择编号、源身份、源范围、字节长度、SHA-256、`twilight-stem-arrangement-1` 和随机本次执行编号。二阶段重新读取前复核源与原始分轨摘要。原生引擎在使用任何一侧前验证双方材料，拒绝旧策略与过期编号；损坏的一侧使双方回退基础材料，并恢复基础低频 DSP。

## 本轮实际验证

固定 36 组 corpus SHA-256：`ee2c8f460725307331ee76fe866ef0a4b1d9ea332083eb6b8fc595827cb31520`。重新核对原始音源与分析窗口摘要，并通过原生 JSON 窗口导出器检查 72 个模式计划；起止帧、速率、策略、效果及失败原因与 .5 一致：

| 基础规划指标 | .5 | .6 |
| --- | ---: | ---: |
| Natural 智能准备 | 26/36 | 26/36 |
| DJ 智能准备 | 34/36 | 34/36 |
| DJ 混音 ≥16 秒 | 22/36 | 22/36 |

本轮没有修改候选选择或扩大混音时长。分轨是在成功选点之后处理材料；上述基础规划结果不能算作分轨带来的覆盖提升。

真实分轨检查覆盖 **9 组歌曲对、10 个过渡**：2 个 Natural，8 个 DJ。使用生产宿主导出的真实 PCM、固定 Demucs GPU 推理及原生准备；全部实际使用双侧分轨材料，没有回退。针对单声部与弱冲突也保留样本，不以增强次数越多作为质量标准。

| 过渡 | 发生处理的声部 | 重叠 RMS 积分降低 |
| --- | --- | ---: |
| pair-12 DJ | 人声 | 9.8% |
| pair-15 DJ | 贝斯 | 11.2% |
| pair-17 DJ | 贝斯 | 74.3% |
| pair-24 DJ | 人声 | 4.4% |

这些是工作进程在实际淡化增益下计算的声部强度代理指标，单位为 RMS 振幅乘秒；不是可听重叠秒数、感知质量评分或人工验收。试听输出还包含生产材料边缘融合、变速、效果及共享 headroom。与基础和旧固定分轨处理各生成一份音频，共 **30 个 24 bit WAV**；各组使用同一试听增益、相同原生计划，逐份记录摘要。三种处理在 C/SSE2/AVX2 上渲染通过，差异上限 0.0002，端点逐样本一致，内部峰值 ≤0.9801。

缓存复用的实际运行没有加载模型、导入 Torch 或初始化 CUDA；CPU 无缓存路径实际推理成功，受控原始声部临时文件清理通过。GPU 推理、缓存复用和 CPU 无缓存路径各有资源记录，不能以一次缓存运行代表 CPU 推理。
