# M2.2 执行细案：从本地标签和平台条目自动识别音乐身份

日期：2026-10-24。状态：**分层身份、自动调度、历史恢复及跨实体查询共享的后端实现已齐，生产 Electron 验收待恢复**。本批实现与证据见 [M2.2 实施记录](D:/Project/Twilight_Echo/docs/unified-music-library-m2.2.md)。承接 [M2 总细案](D:/Project/Twilight_Echo/docs/unified-music-library-m2-plan.md) 与 [M2.1 实施记录](D:/Project/Twilight_Echo/docs/unified-music-library-m2.1.md)；下游资料、分类、评价与发布见[后续交付细案](D:/Project/Twilight_Echo/docs/unified-music-library-delivery-design.md)。

## 1. 用户导入后应该发生什么

导入歌曲或保存平台内容后，先正常浏览、播放；Core 根据已有标签和来源 ID 识别人物、录音、专辑项目和具体发行。可靠身份自动确认，不确定的结果保存为候选。用户不需要自行查找或填写 MusicBrainz ID。

```text
本地扫描提交／平台真实库成员发布
  → 收集已有身份依据
  → 按人物、录音、专辑项目、发行分别生成候选
  → 明确依据且无矛盾：确认关联 → 请求允许使用的资料
  → 只有相似度或有冲突：保存候选 → 等待复核
  → 信息不足：保留原条目和播放能力
```

M2.2 完成自动触发、分层识别、持久候选和确认／纠正后端。百科资料继续使用 M2.1 链路；平台正文、图片和 credits 在 M2.3 接入，原页面与收件箱交互在 M2.5 接入。流派树、分类和版本浏览仍在 M3；个人歌曲／专辑评分仍在 M4。

## 2. 两类资料源共同工作，不把 MusicBrainz 当准入门槛

**采用“内部身份独立于供应商，百科与平台分别提供资料”的结构。** MusicBrainz 擅长跨来源关系与发行结构；平台擅长自己的歌手、曲目和中文内容。平台有歌手而 MusicBrainz 没有时，照样保留该平台人物身份；不能把缺少 MBID 解释成没有这位歌手。

| 已有信息 | 识别方式 | 可以使用的资料 |
|---|---|---|
| 本地文件有有效 MB 人物 ID | 查询实体类型、原始标签及矛盾项，分别确认人物 | 已确认人物的百科资料 |
| 本地只有人名／曲名／专辑名 | MB 和用户允许的平台召回，逐层验证 | 确认前只展示候选摘要，不把候选传记放进本地人物页 |
| 平台歌曲有结构化歌手 ID | 在该平台命名空间内直接定位歌手 | 该平台允许的来源上下文资料，无需先有 MBID |
| 平台人物与 MB 人物有可核实关系 | 确认跨源关联 | 共用允许跨来源使用的事实，平台受限正文仍单独保留 |
| 仅确认了本地人物对应某平台歌手 | 保存来源关联，不强造 MBID | M2.3 可读取获准在本地上下文展示的平台正文；未获准时只保留关联 |
| 名称／标签不足以识别 | 不发无意义的反复查询 | 原文件名、占位及人工查找入口 |

**身份相同与正文可复用是两件事。** 不拼接多个供应商的段落，不生成无来源传记；没有正文时显示有出处的简述或“暂无介绍”。

## 4. 身份、候选与资料的存储调整

### 4.1 一个内部目标允许多个外部引用

- 内部 UUID 保持稳定；外部引用用 `provider + entityKind + idType + value` 唯一限定。MBID、网易云歌手 ID、其他平台歌手 ID 不能互相替代。
- 扩展现有 `metadata_entities`，由独立外部 ID 映射连接内部目标。保留 M2.1 的目标 ID、事实、人工值和历史关系；迁移时不按名称合并旧目标。
- 将 `mbid` 从必需关联依据改为一种外部引用。旧明确 MBID 请求继续可用，不增加平台登录等新前提。
- 每个来源按层次分别建立关联：artist、recording、album_project、release。专辑项目是新增实体，不把 M1 的 release 全部改名。扩展 catalog kind、查询校验和关系投影，旧 kind 的意义保持不变。
- 来源范围的未确认人物仍可存在；平台原生 ID 只证明该平台实体，不能自动连到其他平台或某个 MB 人物。
- 若需要把已有两个目标纠正为同一个，采用可撤销映射及冲突预览；不物理吞并人工覆盖。跨源冲突资料由用户选择保留范围，不能自动搬移。

### 4.2 候选保存的是证据，不只是一个分数

每个 candidateId 保存：来源实体、识别层次、外部引用、显示摘要、原始依据、匹配项、缺项、矛盾项、召回供应商、输入版本、matcherVersion、创建时间及状态。

`unresolved / candidate / confirmed / rejected` 表示身份状态；任务的 `queued / running / needs_review / completed` 仍表示执行状态，不能混为一个字段。解除关联保留历史与重新采用限制。

拒绝与解除的抑制按“来源／层次／外部引用”持久保存。改名、重启或更新算法不能自动洗掉用户拒绝；用户明确重新查找可以看见被拒绝项，但重新采用仍需确认。

同名人物现在可以共享候选查询响应，不能共享确认结论。第八批在 Core 增加有界会话缓存和独立取消，候选及证据仍逐实体生成。复核按候选与来源逐条检查版本和冲突；不能因为一首歌已确认，就把全库同名人名一并绑定。

## 5. 分层识别的具体顺序

### A. 先使用已有稳定 ID

- 本地：保留 MusicBrainz artist／album-artist／recording／release／release-group ID，以及 ISRC、条码、厂牌目录号等实际可取得的标签。多人 ID 保留顺序；无法可靠对齐姓名与 ID 时只保存未对齐依据。
- 平台：使用歌曲实际返回的 track／artist／album ID，不从标题或任意 URL 提取猜测 ID。
- 查询验证 ID 存在、实体类型及明显矛盾。文件标签的 artist 与 album-artist 分开；Various Artists 不能成为每首歌的表演者。
- ISRC 只能辅助定位录音，不能单独证明具体发行、母带或可换源版本；旧 metadataMatch 只作为召回线索。

本地数据同时记录字段来自音频标签、CUE、文件名推断、手工编辑还是历史补全。新解析保留依据；旧缓存无法还原的字段标成历史来历，不标成原始标签。**不为增加可选字段直接全局提升解析版本、强迫所有用户重读全库**；新入库与本就需要解析的文件顺带采集，用户主动要求的历史深度识别再进行有界定向补读。

### B. 没有 ID 时生成候选

- 有专辑与歌手信息时，优先以本地专辑分组或已保存平台专辑为上下文召回项目／发行候选，再取可验证的完整曲序。
- 本地同名专辑分组只提供召回上下文，不证明是一张完整专辑；混合文件夹、未知总轨数、轨序不明、缺碟或重复轨不能走整专辑自动确认。分组变化只重评受影响成员，不连带确认同名分组。
- 只有人名时查询人物候选，并展示类型、地区、别名及已知作品等实际返回的消歧信息。
- 只有歌曲信息时召回录音／平台歌曲；逐个分析人物、录音与项目关系，不把歌曲搜索结果第一项直接应用到所有层次。
- 简繁、别名和标点归一化只用于召回和比较。合作艺人不按 `/`、`&` 等字符随意拆成确认人物。
- 候选查询有界、按供应商上下文去重；候选集被截断或分页未完成时记录 incomplete，不把“当前页只剩一个”当成唯一候选。

### C. 确认与保留待复核

| 证据 | 决定 |
|---|---|
| 明确且校验通过的原始外部 ID，无矛盾 | 只确认该 ID 对应的层次 |
| 可核实的跨源关系，目标类型与其他已知 ID 一致 | 确认对应关联，保存关系出处 |
| 唯一整专辑候选，完整逐轨校验通过 | 可确认得到证据支持的项目／录音及人物关系；每层分别记录 |
| 仅名称、时长、搜索分高，或只有部分专辑 | 保存候选，等待人工确认 |
| 同名异人、翻唱／现场／重制矛盾、缺轨或轨序不明 | 不自动确认受影响层次，列出具体冲突 |

逐轨比较碟号、曲号、完整标题、全部艺人、时长、版本标记及可用 ID。时长使用保存的原始精度；CUE 使用区间长度，不拿父文件总时长比较单轨。时长容差与缺项规则随 matcherVersion 保存并用固定样例验证，不能把超出容差改写成“近似成功”。

**相同音轨列表可以出现在多个压片发行中。** 整专辑音轨匹配不单独证明具体压片／地区版本；需要相应发行 ID 或条码、目录号、地区／日期等可区分依据。只有项目可确定时，项目已确认、发行继续待定；资料关联不修改原播放来源或现有手工版本选择。

完整专辑的分层关联已接入：本次父专辑自动确认后，在同一个任务完成事务中检查实际成员，各子实体用独立输入／关联版本与抑制记录决定。多压片必须对子 ID 一致；缺项、冲突、同名合作 credit 或子来源超出父专辑时保留复核。只确认可靠 ID 的快路径不传播。父解除使未确认子候选的父证明失效，已确认的子身份独立保留；每个子结果及最多 200 项的截断标记随父任务保存。详见[第六批实施记录](D:/Project/Twilight_Echo/docs/unified-music-library-m2.2.md)。

## 6. 从真实库成员增量调度

第七批已沿用 CoreMetadataService 和现有实体任务服务落地，不新增执行队列权威。SQLite schema 17 的 outbox 与游标只记录调度进度，任务仍由原 metadata_jobs／metadata_demands 执行。

1. 本地目录及平台成员发布事务通过输入／membership 触发器标记受影响实体。平台 staging 未 commit／abort、本地 pending 及历史目录投影未完成时等待；搜索结果缓存、TaskCenter 打开不触发补全。
2. Core 每批最多处理 200 个待识别实体，持久任务／需求与游标同事务发布。只调度真实成员及非 missing 来源；移出库时仅撤销随机私有 demand 对应的自动消费者，人工及其他共享消费者保留，公共 auto 前缀不被重新解释。
3. 历史首次启用保存 catalog 实体 rowid 上界和单调游标；暂停、重启及 worker 替换后恢复。后来新增／修改进入增量标记，不扩大旧上界，不用 OFFSET 或读取全库载荷。开历史或新增供应商不重跑未变化供应商的完成任务。
4. 优先级为人工／当前详情、新入库、历史回填，自动专辑先于成员。每第 4 次领取给等待至少 60 秒的纯自动老任务一次机会。沿用 host 限流、Retry-After 和持久需求共享取消；第八批补齐跨实体同查询响应共享，播放 URL 请求不进入补全队列。
5. 提交检查任务 generation、来源识别输入版本、该层关联 revision、候选 revision、供应商配置／使用上下文。无关资料或扫描更新不使全库任务失效。
6. Core／数据库服务重启后，从持久任务和游标恢复；数据库 worker 丢失的请求不得作为已确认写入自动重放。领取／提交结果未知时重新读取状态，按任务 ID 与 generation 对账。启动、目录发布、供应商及设置变化唤醒调度，5 秒对账兜底，不等待窗口打开。在途关闭自动设置或移除最后成员阻止纯自动结果发布，共享人工需求保持原合同。

确认后的详情任务按内部目标去重。跨未确认实体的同查询响应已按供应商、上下文、方法和完整参数共享：每池 128 项／8 MiB、单项 2 MiB，有效结果 5 分钟、明确未找到 60 秒，命中不续期。平台搜索只保留识别字段，原获取时间随副本返回；候选、曲序和关联证据逐实体重验。取消一个等待者不终止其他消费者；账号／设置／重新注册变更失效对应缓存，Core 恢复受影响的在途 generation。重启仅恢复原持久任务，不把会话缓存作为任务权威。详见第八批实施记录。

## 7. 为 M2.3 固定平台资料的消费契约

M2.2 建立平台身份引用与候选适配；以下正文合成在 M2.3 实施，不提前改变旧平台页面。

- 平台 `fetchArtistIntro` 字符串在 Core 包装为事实，保留原文；语言未知时记录 und，不因为平台是中文平台就虚构语言和作者。
- 能力策略记录供应商、方法／端点、字段、来源上下文、是否允许缓存／跨源展示／导出及期限。没有可核实使用条件时，不把平台正文复制到本地共享资料；平台原页既有能力继续按原合同使用。
- 同一平台人物可直接使用其原生 ID；本地人物复用前必须确认关联并通过跨源使用策略。没有 MBID 不妨碍这条路径。
- 合成顺序：人工指定／明确清空 → 当前来源的有效自有字段 → 已确认且在当前上下文获准的外部事实 → 原展示兜底。
- 对可用的介绍正文，先按用户语言选择，默认简中 → 繁中 → 英文；同语言的本地共享正文默认百科优先、平台补充，用户可指定来源。百科只有英文而获准的平台有中文正文时，可用中文，保留英文百科切换入口。结构化简述与完整正文分开，不伪装成完整传记。
- und 不视作简中命中；没有首选语言正文时，可作为“语言未标明”的候补，用户也可显式选择。平台后续返回可靠语言信息时更新该事实，不为排序猜填语言。
- 每次显示一份明确来源的正文，其他来源作为可切换资料；断网读允许的缓存。平台禁用或授权变化只处理该范围的事实，不清除人工值和身份历史。
- 专辑正文采用新增可选方法及共享 DTO；现有 fetchAlbumTracks 不等于专辑介绍接口。同步插件声明、宿主白名单、校验与实际实现，不提高所有插件的最低必需接口。

## 9. 验收用例与继续条件

固定样例先覆盖：带 MBID 本地歌；只有歌手／专辑名的完整专辑；单曲／部分专辑；有平台 artistId 但 MB 无记录；同名异人；简繁别名；Various Artists／多人合作；多碟、CUE；现场、翻唱、重制；完全无有效标签；用户拒绝后再扫描；同一人物 100 次引用；取消与 Core／数据库 worker 重启。

每项分别记录：人物、录音、项目、发行的预期与实际状态；自动错误关联数、候选量、无信息量、任务／HTTP 请求数和人工覆盖是否保留。自动确认样例不允许错误关联，不能用覆盖率抵消错误；真实服务只做限流内抽样，故障与恢复用 fixtures。
