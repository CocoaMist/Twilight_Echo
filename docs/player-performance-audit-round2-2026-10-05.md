# 播放器性能复查：第二轮（2026-10-05）

本轮继续检查上一轮优化之外的播放启动、手动切歌、卷积 DSP、可视化数据传输、歌词内容失效、分析任务与长期缓存清理。生产代码未作修改；新增本报告和可复现的隔离测试证据。

结论：确认 1 项高优先级实时处理问题、2 项中优先级重复工作问题、3 项低优先级边界或长期运行问题。应首先处理卷积峰值及保护机制，再处理队列内容与游标的分离、歌词内容的精确失效。

## 测量方法与适用范围

- 本机 CPU：AMD Ryzen 9 7845HX，12 核、24 线程；Windows；Node v24.21.0。
- 原生测试使用本机 MinGW g++，`-O2 -std=c++20`，直接链接当前源码中的卷积、FFT、队列组件。匹配采样率的 float32 WAV 脉冲响应由测试生成，未使用 FFmpeg 解码。两个独立运行均保存原始结果。
- 卷积覆盖 48/96/192 kHz、2/8 声道、0.125/2/8 秒 IR，共 18 种组合；每种预热 64 次，测量 512 次，每次 256 帧。回调期限按 `帧数 / 采样率` 计算。表中的“超期”指组件处理时间超过这一期限，不是实测声卡掉音次数。
- 可视化使用 8192 FFT、192 kHz、8 声道；每种预热 128 次、测量 64 次，读取前注入 256 帧。计时包含频谱更新和 JSON 构造，不包含完整进程通信、主进程聚合或绘制。
- JS 测试调用真实队列准备函数、曲目合并函数和分析管理器；歌词测试提取并执行当前 Vue 组件的 computed/watch 源码及桌面歌词发布函数，使用真实 Vue 响应式和歌词解析器，替换视口几何操作与 IPC 接收端。歌词计时不包含真实 DOM 排版、动画、桌面窗口处理。
- 未进行真实声卡连续播放、网络断流或数小时整机堆快照测试；因此不能据此声称所有设备都会爆音，或者已排除全部内存泄漏。
- 原始数据中的 `p999Ms` 在 512 个样本的该实现里取样本最大值，与 `peakMs` 相同，不将它解释为长时间播放的可靠尾延迟估计。

## 1. P1：卷积的周期性计算峰值超过实时期限，保护机制不能覆盖这种负载

代码位置：[分区触发与计算](D:/Project/Twilight_Echo/audio-engine/dsp/ConvolverProcessor.cpp:150)、[回调预算和保护](D:/Project/Twilight_Echo/audio-engine/dsp/ConvolverProcessor.cpp:251)、[分区选择](D:/Project/Twilight_Echo/audio-engine/dsp/ConvolverProcessor.cpp:706)。

每个声道积累满一个分区后，在当前 `process()` 内完成正向 FFT、所有 IR 分区的频域累加和逆 FFT。声道边界同步，重活集中在同一回调。4096 帧分区配合 256 帧回调时，每 16 次出现一次重计算。

| 配置，均为 256 帧 | 回调期限 | 两轮峰值 | 超期次数，第一轮 / 第二轮 | 两轮结束状态 |
| --- | ---: | ---: | ---: | --- |
| 48 kHz，2 声道，0.125 秒 IR | 5.333 ms | 0.780 / 0.407 ms | 0 / 0 | 活动 |
| 48 kHz，8 声道，2 秒 IR | 5.333 ms | 11.839 / 8.817 ms | 32 / 32 | 活动，未旁路 |
| 96 kHz，2 声道，8 秒 IR | 2.667 ms | 8.454 / 6.217 ms | 32 / 32 | 活动，未旁路 |
| 192 kHz，2 声道，0.125 秒 IR | 1.333 ms | 2.574 / 1.930 ms | 32 / 32 | 活动，未旁路 |
| 192 kHz，8 声道，8 秒 IR | 1.333 ms | 71.138 / 48.918 ms | 32 / 32 | 活动，未旁路 |

这不是单个偶发峰值：多个组合稳定出现 32/512 次超期，与分区计算周期一致。48 kHz 双声道 8 秒 IR 的结果会随本机状态改变：第一轮 17 次超期，第二轮 0 次；不把这个边界配置当作稳定失败样例。

保护机制存在两个独立缺口：

1. `consecutiveOverruns_` 必须达到 3 才旁路。重计算之间的轻量回调把它清零，周期性严重超时永远无法累计到阈值。
2. `budgetMs = max(2.0, blockMs * 0.5)` 的下限比 192 kHz / 256 帧的完整期限 1.333 ms 更大。第二轮 192 kHz 双声道短 IR 已超期 32 次，但 `overrunCount` 为 0，说明保护连这些超期也没有记录。

潜在表现是 DSP 开启后低延迟输出出现断续或爆音；组件测试确认实时风险，具体设备表现仍须设备验证。长 IR 多声道还占用较多工作内存：192 kHz / 8 声道 / 8 秒配置的组件报告为 394,397,280 字节，约 376 MiB。这是当前算法的已分配状态量，不能据此称为泄漏；实际图代际、预加载与控制图可能增加整机占用，本轮未测总峰值。

建议：先以真实回调期限和整条 DSP 链余量计算预算，增加窗口内累计超期或分区周期感知的退避策略；再将长尾 IR 工作分散到多个回调，评估非均匀分区或有明确延迟约束的异步计算。仅改变分区大小不能保证解决累计计算量和尖峰问题。恢复旁路应带退避，避免反复重启再次产生尖峰。

验收：覆盖上述矩阵、不同回调帧数、路由矩阵及 IR；验证每 16 次出现的超时也能触发保护，预算小于 2 ms 时能正确识别超期，并验证音频输出、算法延迟与恢复行为。现有 [音频性能门禁](D:/Project/Twilight_Echo/audio-engine/tests/audio_performance_gate.cpp:33) 固定 44.1 kHz、双声道、512 帧，无法代表这些高采样率小缓冲配置。

## 2. P2：同一队列中手动切歌，重复授权、传输和解析完整队列

代码位置：[loadAndPlay](D:/Project/Twilight_Echo/src/renderer/src/stores/usePlayerStore.ts:2913)、[队列准备](D:/Project/Twilight_Echo/src/renderer/src/utils/nativeQueuePreparation.ts:75)、[主进程授权](D:/Project/Twilight_Echo/src/main/audio/engineIpc.ts:761)、[队列去重条件](D:/Project/Twilight_Echo/src/main/audio/playbackController.ts:637)、[原生解析](D:/Project/Twilight_Echo/audio-engine/playlist/QueueManager.cpp:384)。

手动选择曲目走 `loadAndPlay` 时，会停止原生播放、解析来源、准备全队列、提交队列、同步播放模式，再启动当前曲目。队列 JSON 相同但索引改变时，主进程的短路条件不成立，原生 `LoadQueue` 仍清空并解析每个队列项，重建播放顺序。

真实队列准备函数的隔离测试：同一个 5000 项本地队列，依次选择 12 个不同索引，发生 12 次当前文件授权和 12 次全量批量授权，总计提交 60,000 个批量授权目标。这里授权桩立即返回，1.22 ms 中位仅代表 JS 准备成本，不能作为实际启动耗时。

实际主进程的预检查和队列提交又分别解析文件权限；[路径解析](D:/Project/Twilight_Echo/src/main/security/pathGrants.ts:6) 每次执行 `realpath` 和 `stat`。请求内去重、16 并发已经减少同一次请求的风暴，但没有消除手动切歌时重复提交相同队列的工作。对 N 个互异本地来源，渲染预检查和主进程队列提交各有一轮 N 项解析，另有当前来源检查和播放入口检查；磁盘成本未在本轮量化。

原生同一 JSON 换索引的 5000 项测试，两轮加载中位分别为 24.210 / 20.681 ms；峰值 26.814 / 33.170 ms，JSON 长度 592,781 字符。此数字仅包含队列管理器解析，不包含授权、JS 序列化、跨进程传输和解码启动。

边界核对：当前 IPC 上限为 5000 项。20,000 项渲染测试正确降级为当前一首，没有进行全量批量授权；原生 20,000 项的 99.755 / 85.580 ms 测量仅用于组件扩展性观察，不代表当前 UI 会向原生发送这么大的队列。原生委托的自动下一首有快捷路径，也不能用手动切歌结论概括全部自动切歌。

建议：为队列内容建立修订号，将“替换队列”和“选择已有条目”分开。队列未变时只提交条目身份或索引；路由、ReplayGain、CUE、顺序等实际内容变化才重新提交。保留主进程对当前播放来源的最终授权，不能通过长期信任渲染层路径来换取速度。快速连点时还应让过时的准备任务尽早取消。

验收：5000 项不变队列连续手动选择，完整队列加载和全队列授权次数不随选择次数增长；同时覆盖重复歌曲、CUE、随机模式、过期在线地址、删除文件和权限变化。

## 3. P2：歌词内容未变，曲目对象更新仍导致重新解析、重定位和完整发布

代码位置：[曲目合并](D:/Project/Twilight_Echo/src/renderer/src/utils/playerTrackUtils.ts:54)、[播放信息更新赋值](D:/Project/Twilight_Echo/src/renderer/src/stores/usePlayerStore.ts:1304)、[歌词 computed](D:/Project/Twilight_Echo/src/renderer/src/components/PlayingMusic.vue:274)、[两个重新居中 watcher](D:/Project/Twilight_Echo/src/renderer/src/components/PlayingMusic.vue:409)、[桌面歌词监听](D:/Project/Twilight_Echo/src/renderer/src/app/useDesktopLyricsPublisher.ts:148)。

队列快照没有完整歌词，而当前曲目有歌词时，`mergeTrackTransientData` 为同一首歌生成新对象。非切歌的播放信息更新仍把它赋给 `currentTrack`。`managedLyrics` 每次生成新投影对象，随后 `buildLyricLines` 和显示行映射重新计算，两个 watcher 各请求一次 `recenter('snap')`。

桌面歌词开启时，发布器监听整个曲目引用，每次都重新解析全文、投影、增加 `contentRevision` 并发布完整会话。时钟和内容已经分离，但内容失效条件仍过宽。

| 歌词量，20 次内容不变的曲目更新 | 页面解析 | 桌面解析 / 全量发布 | 请求重新居中 | 累计发布字符数 | 更新处理中位 / 峰值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 300 行 LRC | 20 | 20 / 20 | 40 | 422,252 | 1.28 / 2.64 ms |
| 3000 行 LRC，压力场景 | 20 | 20 / 20 | 40 | 4,486,272 | 8.70 / 12.29 ms |

这是对真实响应式源码的隔离复现，几何和 IPC 接收端使用桩，计时不能代表真实页面帧率。`recenter` 的请求数也不等同于 40 次完整浏览器排版，但说明同一次内容更新会重复请求重定位。

发生频率须准确限定：正常 `position` 更新已被播放信息签名去重；实际原生字段 `lastProcessMs` 单独变化也不会改变当前签名，两项均已测试。因此本问题出现在确实到达 renderer 的播放信息刷新、元数据替换或管理文档变化时，不能声称正常播放每 250 ms 都重解析。桌面歌词关闭时不发布桌面会话；页面端的失效仍存在。

建议：以曲目身份、原文/译文/音译内容和当前曲目的覆盖选项作为解析依赖，稳定内容引用；展示偏好与偏移应只改变投影或时钟。桌面内容修订号只在实际会话内容变化时增加。同一次内容变化统一请求一次重新居中，元数据和诊断刷新不打断歌词运动。

验收：同 ID、同文本的对象替换不重新解析，不发布新内容修订，不请求 snap；真实歌词替换、语言层选择、偏移、CUE 条目切换继续正确更新。应同时测试 LRC、逐字歌词和 TTML。

## 4. P3：批量授权的异常退化路径重新引入无上限并发

代码位置：[authorizeLocalTargets 的 fallback](D:/Project/Twilight_Echo/src/renderer/src/utils/nativeQueuePreparation.ts:201)。

批量 API 缺失、抛错或返回长度不匹配时，代码执行 `Promise.all(unique.map(...))`，一次创建所有单文件授权请求。本轮让真实批量边界抛错，1000 个互异本地文件产生 1001 次单文件请求，峰值并发 1000；多出的 1 次来自当前曲目预检查。

正常批量路径已经有 16 并发，因此这个问题只在兼容/异常路径出现。应给单文件退化路径也设置并发上限，并在加载已过时后停止继续派发。验收覆盖 batch 缺失、拒绝和畸形答案，确认峰值并发始终有界且授权判定语义不变。

## 5. P3：分析失败记录冷却过期后仍保留，成功重试也不删除

代码位置：[失败 Map 和冷却检查](D:/Project/Twilight_Echo/src/main/audio/fileAnalysisManager.ts:71)、[失败写入](D:/Project/Twilight_Echo/src/main/audio/fileAnalysisManager.ts:158)、[显式清空](D:/Project/Twilight_Echo/src/main/audio/fileAnalysisManager.ts:213)。

`failures` 只检查冷却时间，没有容量上限或过期清除。正常成功和缓存命中也不删除此前失败项。响度管理器有显式 `clearFailures()`，但不能代替普通请求路径的回收；BPM 管理器同样继承这一 Map。

用 256 个真实临时文件和失败分析桩产生 256 条记录，将注入时钟推进超过 10 分钟冷却期，256 条全部过期仍在 Map 中。随后成功重试一首，结果为 `completed`，Map 仍为 256。同期 `inFlight` 和 `activeGenerations` 均归零，未把正常在途清理误判成泄漏。

这是按失败过的不同路径累积的长期保留问题，单条体积小；本轮未测整机堆增长，优先级低于实时和切歌问题。建议成功时删除该路径的失败项，过期项按请求或批次清理，并设置最大记录数，保留冷却抑制语义。验收覆盖大量互异失败路径、时钟推进、成功/缓存命中与取消。

## 6. P3：可视化仍有原生侧的数据生成与序列化优化空间

代码位置：[可视化参数](D:/Project/Twilight_Echo/src/renderer/src/components/AudioVisualizerPanel.vue:27)、[原生 JSON 构造](D:/Project/Twilight_Echo/audio-engine/dsp/FftSpectrumAnalyzer.cpp:325)、[主进程柱状聚合](D:/Project/Twilight_Echo/src/main/audio/audioEngineHelpers.ts:992)、[服务同步调用](D:/Project/Twilight_Echo/src/main/audioEngineService.ts:114)。

全屏可视化请求 4096 点频谱，主进程将其聚合为 140 根柱子后清空原始频谱，再发给 renderer。渲染层与 iframe 已避免接收完整频谱；剩余成本在 native 到音频服务/主进程这一段：生成数千个 JSON 数值，服务响应传输，再解析和聚合。

| 原生查询 | 两轮 JSON 构造与分析中位 | JSON 字符数 |
| --- | ---: | ---: |
| 64 点频谱，48 点波形，无历史谱 | 0.640 / 0.545 ms | 1,222 |
| 2048 点频谱，256 点波形，无历史谱 | 1.282 / 1.066 ms | 7,695 |
| 4096 点频谱，256 点波形，无历史谱 | 1.933 / 1.469 ms | 13,555 |
| 4096 点 × 96 帧历史谱，256 点波形 | 120.215 / 93.604 ms | 1,054,194 |

最后一行是公开接口的上限压力测试，当前 UI 的 `spectrogramFrames` 为 0，没有使用这个历史谱配置；不能把 100 ms 级结果当作当前全屏页面的常态。服务内的 native 调用是同步的，大查询会延迟同一服务消息循环处理控制命令，但不会据此推导音频渲染线程阻塞。

还专门核对了 64 KiB N-API 初始缓冲：缓冲不足时虽调用 C API 第二次，底层 [copyJsonWithProbeResult](D:/Project/Twilight_Echo/audio-engine/core/TwilightAudioEngine.cpp:2557) 会复用第一次结果，**不存在第二次重新计算完整 JSON**，不应将它列为重复计算问题。

建议：在原生侧保留 8192 FFT 的分析精度，提供直接返回 140 根 log-Hz 柱子的按需投影，避免全频谱先序列化再丢弃；不要简单把请求改为 64 点而损失频率分布。对未来历史谱消费者采用增量帧或 typed buffer，并设置数据量预算。当前 1–2 ms 组件成本尚不足以认定为主要卡顿原因，放在后续优化。

## 建议实施顺序

1. 卷积保护预算与周期性过载识别，随后消除分区计算尖峰，补高采样率/小回调门禁。
2. 队列内容修订与游标操作分离，保留来源安全校验并覆盖逻辑条目身份。
3. 歌词解析、桌面发布的内容级依赖和单次布局触发。
