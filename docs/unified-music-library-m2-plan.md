# M2 实施细案：让本地和流媒体共用可追溯的音乐资料

日期：2026-10-23。状态：**计划已细化，尚未实施**。主记录：[统一音乐库计划](D:/Project/Twilight_Echo/docs/unified-music-library-plan.md)。前置成果：[M1 实施记录](D:/Project/Twilight_Echo/docs/unified-music-library-m1.md)。

## 1. 先交付什么

用户导入文件或保存平台歌曲后，立即按现有方式浏览和播放；Core 在后台识别人物、专辑项目和具体发行，补充介绍、图片和基础人员资料。已确认的同一人物或专辑共用资料，未确认的关联进入曲库整理收件箱。

**M2 的主线是“确认身份 → 保存有出处的资料 → 可恢复任务 → 原页面展示”，不是多接几个搜索 API。** 缺少具体发行信息不妨碍使用已确认的专辑项目介绍；找不到介绍时，展示有出处的结构化概览，不生成传记或乐评。

- M2 交付人物／专辑介绍、图片、分层识别、基础 credits、出处、覆盖、纠正、撤销与后台任务。
- M3 负责流派层级、分类映射、发行版本浏览和统一自动选源。M2 可以保存允许使用的原始流派和发行属性，不提前宣称分类已完成。
- M4 负责歌曲／专辑星级、收藏、禁播、标签和 Focus。M2 不把匹配分数、播放量或音质规格转换成评分。
- M5 完成人物参与内容、作品探索、完整个人备份迁移及发布验收。M2 中引入的用户覆盖和关联记录必须保留可导出数据，不能依赖可清理的外部资料缓存存活。

## 3. 身份和事实必须分开保存

### 3.1 人物、录音、专辑项目、发行分别确认

沿用 M1 的来源实体和 UUID；新增 `album_project` 表示专辑项目，对应 MusicBrainz release-group。现有 `release` 不批量改名为专辑项目，也不因为取得一张封面就变成已确认发行。

每一层分别记录 `unresolved / candidate / confirmed / rejected`、依据与版本。人物、录音、专辑项目可以先确认，具体发行继续待定。旧 `identity: source | manual` 描述现有目录身份来源，不直接冒充这套识别状态。

- 外部 ID 唯一键为“供应商、实体类型、ID 类型、外部 ID”，指向内部 UUID。平台人物 ID 只在对应平台内有效。
- 用可撤销关联连接来源实体与已确认实体，保留原实体和来源事实，不物理吞并旧实体。一个外部身份只拥有一份共享资料，多个来源通过关联读取它。
- 身份资料关联不修改既有手工版本／版本族的权威，也不授予换源资格；M2 不新增自动切换播放来源。
- 拒绝和拆分记录落库。相同候选不会在后台下次刷新时重新自动采纳；明确重新查询可以展示它，但重新关联仍需用户选择。
- 关联前比较已有人工覆盖；存在冲突时预览并选择，自动任务不能替用户迁移或覆盖这些值。撤销只移除关联，原来源与原值仍可恢复。

**自动确认的依据**：一致且无矛盾的明确 ID／跨源关系，或唯一整专辑候选并完成逐轨校验。MusicBrainz 搜索分、标题／艺人／时长相似、旧 `metadataMatch` 的 high 标记都只用于召回与排序，不直接升级为确认身份。

整专辑校验比较碟号、曲序、标题、全部艺人、时长和版本标记；多候选、缺轨、现场／重制等矛盾保留待确认。已确认录音出现在某张发行中，不等于本地文件来自该发行。多人 credits 保留顺序和 joinphrase，不从一个人名字符串猜造多个人物。

### 3.2 本地标签不全时，也能逐层前进

1. 有人物／专辑标签、没有介绍：优先识别这些实体；确认后补资料，不要求先识别每一首录音。
2. 只有曲名或部分标签：用现有平台和 MusicBrainz 召回歌曲、专辑及人物候选；每个原条目分别校验证据，不把第一个搜索结果直接入库。
3. 只确认人物：先显示人物资料；只确认专辑项目：先显示通用背景并标记“具体发行待确认”。
4. 文件名也没有有效音乐信息：保留可播放的本地条目，允许用户搜索／确认候选。没有声学证据时不宣称可以自动识别任意无标签文件。

指纹识别维持后续可选接入，单独取得联网启用选择，不作为 M2 基础链路的前提。

### 3.3 资料仓库的最小内容

新增表随下列工作包落地，不提前建立 M3—M5 空表；命名沿用实施时数据库约定。

| 数据 | 必须保存的含义 |
|---|---|
| 外部身份与关联 | 原实体、确认目标、类型、依据、来源、确认方式、拒绝／拆分记录、revision |
| 资料事实 | 目标实体与层次、字段、值、语言、供应商及其实体 ID、获取时间、来源修订、有效期与适用上下文 |
| 出处与素材 | 来源页面、资源标识、作者、署名文本、许可与许可链接；正文和图片分别记录 |
| 人工覆盖 | 目标稳定实体、字段、指定值／明确清空、语言、更新时间及 revision；恢复自动值与清空是不同操作 |
| 人员关系 | 人物 ID 或未确认的来源人物引用、原角色、规范角色、挂载对象、顺序、关系属性和出处 |
| 候选与任务 | 候选依据、请求／输入版本、任务状态、generation、下次重试时间、持久游标和迁移标记 |

没有人物 ID 的历史 credits 先作为来源范围引用保留，不凭名字创建共享人物。M2 展示已取得的基础角色；完整人物参与内容和作品关系页面留在 M5。

展示继续使用：**人工指定／明确清空 → 当前来源有效标签 → 已确认且允许使用的外部事实 → 现有展示兜底**。

- 外部事实不回写音频、CUE 或平台账号，也不通过修补扫描字段来保存传记；列表所需补缺由可重建投影提供。
- 当前来源和实体的值分层保存。本地有效封面／标签优先，平台在其允许的来源上下文展示自己的资料，不因共享身份突破使用范围。
- 首发日期与具体发行日期分开，保留年／月／日精度。
- 介绍按简体中文 → 繁体中文 → 英文选择，显示实际语言。中文维基的 `zh-hans`／`zh-hant` 是同一条目的呈现变体，不虚构为两个独立资料源；若转换显示，记录原语言和转换方式。
- 明确清空字段后，不从另一语言或另一供应商补回来；“恢复自动值”才解除覆盖。
- 自动刷新只替换同供应商对应事实。暂时错误不清空已有有效资料；许可或有效期要求删除时只处理受影响内容，保留允许保存的身份记录和用户值。
- 旧本地补全的补缺／手工采纳效果保持兼容；历史自动填充与新身份确认分别解释。无法还原逐字段来历的旧值保留为历史资料，不把它们重新标成从文件读出的原始标签，也不批量清空它们。

## 4. 供应商接入顺序与能力边界

采用 Core 内的 `MetadataProvider` 协议：声明实体类型、字段、候选／详情／关系能力、端点、预算及缓存／展示／导出限制；接受取消信号，返回有出处的类型化结果，不直接写主库。Core 校验后提交。

| 来源 | M2 使用方式 | 失败或能力不足时 |
|---|---|---|
| MusicBrainz | 人物、录音、专辑项目、发行及关系；先明确 ID lookup，再增加候选检索。保存人员和 release-track ID，角色不再只筛 producer | 无匹配记为未找到，歧义待确认；503 等待重试；genres／ratings 不随核心结构默认放行 |
| Wikidata → Wikipedia | 沿已确认 MB 链接、QID 和 sitelink 取得结构化概览及多语言正文；无已确认链接时只能形成候选 | 消歧义／错误类型不采用；无正文显示结构化资料或“暂无介绍” |
| Commons | 按已确认人物的图片引用读取逐图作者与许可 | 缺许可资料或不允许使用则不用；不抓别人的艺人照片替代 |
| Cover Art Archive | 确认发行后取该发行图片；只确认项目时允许项目封面回退，清楚标记层次 | 无图保留原封面或占位；图片命中不能反向确认发行 |
| 已启用流媒体 | 通过现有 Core 插件 RPC，按来源 ID 查询实际支持的人物、专辑和曲目资料 | 未登录／禁用／方法不支持分别呈现；平台不可用不阻塞本地资料 |

平台简介的字符串要包装为带来源页面、目标 ID、语言和使用范围的事实。需要新增专辑详情能力时，采用**可选方法和共享 DTO**，同步宿主白名单、声明与校验，只让真正支持的平台声明；不修改所有平台的最低必需接口。

开发／测试和商业发布分别使用部署策略。策略按“供应商 × 端点 × 字段 × 使用范围”判断；`enabled` 不等于内容可以跨来源复用。关闭某个字段应返回可解释的不可用原因，而不是悄悄换抓取端点。CAA 和 Commons 的图片与 API 返回的结构数据分别判断。

MusicBrainz 使用有意义的应用 User-Agent 与真实项目联系方式；联系方式从应用配置提供，不要求每个用户提交邮箱。商业发布的服务资格由发布负责人核对，未满足的能力在该构建中关闭，不阻塞本地资料模型开发。

Discogs、TheAudioDB、Last.fm、AcoustID 暂不增加首轮必需依赖；已有 QQ 补充资料保留出处，联网刷新受同一能力策略控制，不提升为稳定的通用官方开放接口。

## 5. 一个 Core 调度权威，任务和网络请求分层去重

扩展现有 CoreMetadataService，由它统一拥有实体任务和既有本地补全适配路径。现有 `metadata.start / cancel / status / candidates / apply / clear` 的本地曲目含义保留；不要用新的实体级全局取消替代旧调用的行为。

### 任务状态与提交

`queued → running → completed`；中途可以进入 `retry_wait / needs_review / blocked / failed / cancelled`。`completed` 另存 matched／not_found／partial 等结果，不把“HTTP 成功、无资料”算成补齐。`blocked` 明确记录未登录、缺配置或策略关闭的原因，条件变化后才恢复。

- 每个任务存实体、供应商、资料类型、语言、输入版本、generation、尝试次数、nextAttemptAt、批次和消费者。重启重新排队未提交的 running；已提交事实与完成状态在同一 SQLite 事务中写入。
- 提交校验任务 generation、目标关联 revision、相关来源版本和当前策略。无关实体的资料更新不使任务全部失效；不以全局 catalog revision 作为所有任务的提交栅栏。
- 优先级为当前详情／人工 → 新入库 → 历史回填；历史队列仍应获得运行机会。回填沿持久游标分批枚举真实库成员，沿用有界批次，不读取整个平台目录。
- 关闭窗口只解除订阅，不取消任务；退出 Core 保存状态后中止网络并等待已接受写入。清空资料缓存不能同时清除人工覆盖、确认和拒绝记录。

### 去重、限流和恢复

- 任务按“已解析目标实体、供应商、语言、资料类型”去重。同一已确认人物被 100 首歌引用时，只调度一份对应资料任务。
- 任务消费者是持久的补全需求，不是窗口订阅；窗口关闭不会撤销需求。取消批次仅移除该批次需求，不取消其他批次仍需要的共享任务。
- 未确认条目可以共享相同查询的候选响应缓存，但逐个评估关联证据；共享搜索响应不等于合并人物。确认之后再共用该人物详情。
- HTTP 去重按供应商、端点、参数、语言和必要的账号／使用上下文划分；跨账号受限内容不共用。一个消费者取消不终止仍有消费者的请求；最后一个离开才中止，迟到结果不能发布给已取消任务。
- MusicBrainz 公共服务的全部本应用资料请求共享预算，按不超过 1 请求／秒执行，初始保守间隔 1.1 秒、并发 1。旧 Rhine 入口也走同一调度，不能靠各实例 sleep。
- Wikidata／Wikipedia／CAA 等按实际 host 与来源策略共享预算。平台适配器调度元数据 RPC；插件内部的请求和重试需使用其受控请求出口，不能把一次 RPC 限流宣称为其全部 HTTP 已被限流。播放 URL 获取不排在历史补全队列后。
- 429／503 读取 Retry-After 并保存恢复时间，允许服务指定的等待超过本地退避上限；超时／连接失败退避重试。未找到有负缓存，鉴权失败等恢复条件，歧义等用户复核，三者不能混同。

新网络设置区分：启用资料补全、允许的资料源、介绍语言、历史补全与候选查询。首次启用说明发送名称／外部 ID／必要时长；关闭后停止相关新请求并阻止在途结果发布，用户已有资料按使用条件保留。音频、路径、完整曲库和收听历史不随资料任务上传。

## 6. 按六个工作包串行推进

同一音乐库域负责人拥有模型、Core、适配、客户端和验收。下列均为待办；每包交付可观察结果后再进入下一包，不以建表或声明接口代替完成。

### M2.1：先打通一个已确认实体的完整资料链路

- [ ] 增加外部身份关联、资料事实、出处、覆盖、任务和输入版本的必要存储，以及 schema 升级／一致备份。
- [ ] 建立 MetadataProvider 协议和基本部署策略、共享 host 调度、取消／重试；扩展 CoreMetadataService 和数据库有界操作，接一个按明确 ID 查询的 MusicBrainz → Wikidata／Wikipedia 路径。provider fixture 覆盖取消与故障，真实公开样例做小量验证。
- [ ] 提供显式外部 ID 解析 → Core 保存候选 → 人工确认、实体资料查询、针对实体的补全、任务读取／取消及覆盖入口，接入生产 Core；不依赖窗口创建任务或持有请求。

**本包完成条件**：一个本地来源和一个平台来源分别经明确依据关联同一人物，读取同一份带语言／出处的介绍；Core 重启后资料与未完任务可继续；人工值和取消后的迟到结果不会被覆盖。此时只是后端纵向链路，不标记 M2 界面已交付。

### M2.2：让真实入库条目自动进入分层识别

- [ ] 增加现有平台／MusicBrainz 的候选适配和分层匹配，支持人物先确认、专辑项目先确认、具体发行待确认。

## 7. 公共接口和接线范围

下列为新增操作的建议分组，实施时在 [Core 协议](D:/Project/Twilight_Echo/src/shared/coreProtocol.ts)固定命名；旧 Track 级 metadata 操作保持兼容。

| 操作组 | 输入与返回约束 |
|---|---|
| 资料能力／实体资料 | 有效能力、不可用原因；实体 ID、可选来源上下文 → 合成值、分层身份、字段来源、语言及 revision |
| 补全／任务查询／取消／重试 | 有界实体集合或 Core 持久游标范围；返回批次与持久任务 ID。新取消与旧 `metadata.cancel` 分开，重试不绕过 host 冷却 |
| 候选分页／确认／拒绝／解除 | 允许按限定命名空间和格式校验的外部 ID 发起解析；采纳时使用 Core 保存的候选 ID、目标版本和关联 ID，不接受客户端提交任意候选快照、供应商响应或待抓取 URL |
| 字段覆盖 | 明确 set／clear／reset，字段白名单、值类型、大小和 expected revision；冲突返回后重新读取，不静默覆盖 |

查询默认有限页，最大 200；正文、候选和关系另设字节／条数上限，不用无限事实数组替代分页。读取展示允许的来源页面和署名链接，资源访问继续使用受控图片句柄；不暴露私有 source key、文件路径、播放 URL 或凭据。

接线同步覆盖：共享 DTO／请求校验与权限 → 数据库协议／服务客户端 → Core 服务与 application → 生产入口 → 现有主进程桥／preload → Renderer 投影与测试。事件只发送受影响实体、任务批次 ID 和修订号；资料更新不冒充扫描内容更新，不重建当前播放队列。
