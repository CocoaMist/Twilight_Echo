# Echora 界面质检与后续修正方案

本次结合 Apple HIG、Apple Music Windows 用户指南和 Fluent 2，复核当前主仓库的界面修复。结论是：公共导航、确认流程和反馈层已有明显改善，但整体界面暂不通过验收。发现 3 项优先问题，以及 6 项需要继续修正的规范或体验问题。下一轮应先保证小窗排版、外观预览和键盘操作，再继续统一页面细节。

本次遵守“不使用 Computer Use”的要求，仅检查源码、官方文档、已有回归记录和历史截图。完成了 122 个 Vue 文件的模板结构扫描，并人工追踪下文列出的关键操作及样式关系。模板扫描不等于所有业务状态的人工验证，历史截图也不代表最终源码的运行画面。本次没有修改应用源码，没有提交或打包。

## 参考规则怎样合并

Apple Music 没有单独的一套通用 HIG。这里分别使用 Apple 的正式设计规范，以及 Apple Music 官方用户指南描述的产品行为。

| 依据 | 本产品采用的原则 | 使用边界 |
| --- | --- | --- |
| [Apple HIG Layout](https://developer.apple.com/design/human-interface-guidelines/layout) 和 [Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars) | 稳定的信息层级、可预测的导航、尺寸变化后仍能完成原任务 | 不照搬 iOS 的导航形式 |
| [Apple HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) 和 [Typography](https://developer.apple.com/design/human-interface-guidelines/typography) | 支持键盘、清楚的控件名称、可读文本、放大后的完整内容 | 不把 Apple 的 pt 数值直接当作 Windows CSS px |
| [Apple Music 队列](https://support.apple.com/guide/music-windows/queue-up-your-songs-musb1e6d1c76/windows)、[迷你播放器](https://support.apple.com/guide/music-windows/use-the-miniplayer-mus71d7dcfce/windows)、[搜索](https://support.apple.com/guide/music-windows/search-for-music-mus896f20db7/windows) | 音乐库、播放队列和搜索范围各有明确用途；小窗仍可管理接下来的播放内容 | 属于体验参考，不要求复制订阅、社交或 Apple 专属功能 |
| [Fluent 2 Layout](https://fluent2.microsoft.design/layout)、[Typography](https://fluent2.microsoft.design/typography)、[Accessibility](https://fluent2.microsoft.design/accessibility) | Windows 外壳、4px 间距体系、公共字体层级、焦点、缩放与内容重排 | 1024、1440 和高度 800 的产品断点属于本项目选择 |
| [Fluent 2 Dialog](https://fluent2.microsoft.design/components/web/react/core/dialog/usage)、[Message bar](https://fluent2.microsoft.design/components/web/react/core/messagebar/usage)、[Tablist](https://fluent2.microsoft.design/components/web/react/core/tablist/usage) | 统一确认、错误恢复及页签交互 | 采用规范的语义和行为，不要求迁移到 React |

合并后的方向：以 Fluent 2 建立 Windows 界面外壳，以 Apple Music 的音乐任务组织方式检查浏览和播放是否连贯。界面字体采用 Windows 系统字体及中文回退；封面和歌词可以有内容字体，公共按钮、导航与提示使用同一套 UI 字体。外观定制需要有明确边界，不能改坏核心操作的可达性。

## 优先问题

### Q1 迷你播放器的标题被主界面规则覆盖

**优先级 P1，源码可以确定。** 所有窗口都从 `main.ts` 导入 `fluent.css`。公共 `#app h1` 的优先级高于 `.mini-track-meta h1`，也高于 compact、wide 两种小窗标题选择器。因此 compact 原来的 13px、standard 的 14–18px、wide 的 15–19px，都被公共 28px 字号和 36px 行高覆盖。公共标题字体还覆盖了小窗根节点继承的独立字体。

这会破坏小窗固定高度的曲目信息区，并造成标题与歌手字体不一致。是否出现具体裁切仍需最终窗口截图，但样式冲突本身已经确定。不能通过增加更多 `!important` 继续叠加解决。

证据：[公共标题规则](../src/renderer/src/assets/fluent.css) 45–53 行；[窗口共同入口](../src/renderer/src/main.ts) 1–3 行；[小窗样式](../src/renderer/src/mini-player/MiniPlayer.css) 400、887、941 行；[独立字体解析](../src/renderer/src/mini-player/presentation.ts) 119 行。

建议：公共页面标题限定到主窗口或 PageHeader；小窗标题使用自己的明确字号角色。统一字体来源与统一字号分别处理。验收 compact、standard、wide，覆盖 420×220、480×300、900×520，以及跟随字体和独立字体两种配置。

### Q2 常见窗口宽度下主题工作室失去实时预览

**优先级 P1，源码可以确定。** `fluent.css` 在宽度不大于 1440 时对整个 `.theme-preview-pane` 设置 `display:none`。这个区域同时包含预览画面和预览页面切换按钮；当前没有独立的“打开预览”入口。调整颜色、背景或播放器布局时，用户只能看到编辑字段和外壳的部分变化，无法核对目标页面。

1366 宽度的窗口、1920 屏幕使用 150% 缩放时的常见窗口范围，都可能进入这一状态。该问题来自布局重排方式，不需要删除实时预览功能。

证据：[响应式规则](../src/renderer/src/assets/fluent.css) 771、834–835 行；[预览结构及切换控件](../src/renderer/src/components/ThemeStudioPage.vue) 311–378 行。

建议：紧凑布局采用“编辑／预览”切换，或提供可打开的预览面板，保留草稿和滚动位置。编辑与预览共用同一份草稿，离开后恢复当前实际主题。1024、1280、1366、1440 宽度下均能查看预览。

### Q3 核心歌曲与节点操作仍存在键盘缺口

**优先级 P1，源码可以确定。** 本地曲目行只有鼠标和拖动事件，没有焦点入口或播放键盘处理。能够获得焦点的歌曲标题按钮打开的是歌曲详情。多选辅助仅处理 Ctrl/Cmd+A 和 Escape，不能替代逐曲定位、播放或打开该曲目的操作菜单。

声音工作台的节点 `article` 同样只用点击选择，无法直接通过键盘选择节点并进入其编辑区。播放浮层的“关闭浮层”按钮只在 `pointerdown` 中执行关闭；它的 `click` 事件仅阻止传播，键盘激活这个有名称的按钮不会关闭面板。

证据：[本地歌曲行](../src/renderer/src/components/SongList.vue) 2305–2324、2360–2368 行；[多选键盘处理](../src/renderer/src/components/song-list/useTrackMultiSelect.ts) 182–200 行；[DSP 节点](../src/renderer/src/components/dsp-rack/DspGraphCanvas.vue) 153–163 行；[浮层关闭按钮](../src/renderer/src/components/PlayerBar.vue) 1506–1513 行。

建议：为歌曲列表建立逐项焦点和明确的播放动作；支持键盘打开原生曲目菜单。为节点增加选择、编辑和排序的键盘替代操作；浮层关闭按钮的键盘激活必须执行关闭。不能只补 `aria-label` 就认为完成可访问性。

## Apple Music 体验参考带来的产品建议

这些属于下一轮体验选择，与上面的确定缺陷分开。

**统一队列的名称与入口。** 主栏和队列标题仍称“播放列表”，页面导航又使用“歌单”。建议临时待播内容统一叫“播放队列”，保存后的集合叫“歌单”。Apple Music 的 Playing Next 同时支持 Play Next 和 Play Last；当前 Echora 曲目菜单有“下一首播放”，队尾操作主要在已有队列项中。建议在本地与在线曲目菜单都提供“下一首播放／加入队尾”，并在迷你播放器提供查看队列入口。迷你窗口目前只显示队列位置，不能管理待播歌曲。不要因此增加第四种播放器形态。

**统一搜索入口与范围表达。** Apple Music 用同一搜索入口选择音乐库或平台目录。Echora 已有统一查询能力，但本地列表仍用“在线搜索”开关，在线页面用来源选择器。建议采用一致的“当前音乐库／全部来源／指定平台”范围表达；保留需要区分的平台能力，切换来源时保留关键词。此建议不要求删除页面内筛选。

**继续收敛外观设置。** 目前四种首页结构、五种播放页布局、三种播放栏形态，以及多个窗口的外观控制仍然并存。允许内容布局变化，但公共返回、队列、音量、提示和设置入口应固定。下一轮先修 Q1、Q2、Q4，再决定哪些布局确有不同用途；不要继续通过主题增加导航模型。
