# Twilight Echo 基础设施与模块边界检查

检查基线：上游 main `37d5d95`；参照未合并的 [#99](https://github.com/Px-asen/Twilight_Echo/pull/99)（`3944012`）。检查与本地验证在 Windows 完成。此次 PR 的必需 CI 任务也采用 #99 的 Windows 策略。

## 判断与处理

项目已经有 main、preload、renderer、shared 和原生音频引擎的层次，以及 IPC、导入边界、类型、行为和构建检查。目录层次基本明确，但部分运行时职责仍混在大型状态模块中。边界检查通过不能证明模块内部职责已经充分拆分。

| 检查项         | 实际发现                                                                                                                | 本次处理                                                                                      |
| -------------- | ----------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 设置与音频状态 | 通用设置应用在 `audio/state.ts` 中导入窗口、托盘等集成，形成 `window → audio/state → shortcutsTray → window` 的静态循环 | 通用设置与重启移入 `app/settingsRuntime.ts`，窗口颜色选择移入纯函数模块；音频状态保留音频职责 |
| 音频能力规则   | main 与 renderer 各自维护 DoP、Native DSD 和 DSD 状态规则，缺少完整设备字段时会得出不同结果                             | 合并到 `shared/audioDeviceCapabilities.ts`，保留现有消费者导出；候选设备仍需实际探测          |
| 插件版本规则   | 插件目录又实现了一份版本比较，遗漏预发布版本优先级                                                                      | 复用已有语义版本比较器，增加预发布、构建元数据和无效本地清单回归                              |
| 回归约束       | 原有层次检查没有发现 main 内部静态循环                                                                                  | 增加 TypeScript AST 导入与再导出环检查，排除纯类型和懒加载依赖                                |
| CI 所有权      | main 基线仍要求跨平台任务；#99 已按产品结果整合 Windows 检查                                                            | 复用 #99 的工作流、产品结果汇总器和策略检查，保留全部 19 个产品测试入口                       |

## 与 #99 的关系

#99 的网络索引并发持久化、播放生命周期归属、歌词边界和原生音频修复仍由 #99 承担。本次没有重复实施这些功能修复。Windows CI 的共用文件直接取自 #99，以便保持相同的检查策略。

当前 main 的生产依赖审计会阻断 CI：Electron 43.2.0 与 ip-address 10.5.1 存在未豁免公告；#99 已升级为 43.5.0 和 10.7.1。安全门禁保持启用。#99 合并后需要同步依赖并重新执行 CI。

两个 PR 同时修改 `package.json` 的测试脚本。合并时应保留 #99 的完整测试文件列表及网络库基准入口，同时保留产品门禁入口和 `test:local-perf` 的并发上限。

## 剩余结构压力

本次检查后的非测试 TypeScript 文件中，`usePlayerStore.ts` 约 4284 行、`useMusicStore.ts` 约 2349 行、插件 `manager.ts` 约 2232 行，音频管理器、播放控制器和音频 IPC 也仍超过 1500 行。这些是后续按生命周期和状态所有权继续拆分的候选；行数本身不是冗余代码的证据。

已经确认两类具有行为差异的重复规则，并在本次合并。没有进行全仓克隆检测，不能据此宣称项目存在“大量冗余代码”。不应仅按相似文本删除 IPC 适配、平台实现或测试夹具。

## 验证证据与限制

修复前，静态循环、跨进程能力不一致、插件预发布更新回归失败；修复后通过。Windows 上 audio-manager、playback-routing、app、plugins、themes、radio-remote 六个完整测试入口通过；另有一个既有跳过项。测试入口之间有重叠，不能累计为独立用例数量。

完整 Node/Web 类型检查、ESLint、生产构建和渲染资源预算通过。Windows CI 策略与产品汇总器的 27 个检查通过；调整并发后的 local-perf 入口通过 178 项，跳过 2 项。

原生 C++ 未修改；此次没有进行真实 DAC/ASIO 播放验证，也没有执行 Linux 或 macOS 检查。GitHub 生产依赖审计失败发生在远端业务测试之前，不能把本地通过报告成远端 CI 全部通过。
