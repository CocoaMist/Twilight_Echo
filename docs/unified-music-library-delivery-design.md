## 1. 最终用户链路与实施顺序

用户导入一批缺介绍的文件，也保存一些平台歌曲。导入立即可播放；启用补资料后，后台识别人物和专辑，补介绍与图片。用户可以按流派和版本浏览，为歌曲或专辑打分，把“爵士、我评四星以上、近 90 天无播放记录”保存成智能集合，从制作名单继续查看人物和作品。断网仍能使用本地库与允许缓存的资料，个人整理结果可以完整迁移。

**保留一个音乐库域负责人串行交付，每次贯通存储、Core、客户端与该项验收。** 阶段间传稳定引用、状态和出处，不传一份让下游重新猜身份的名称列表。

## 2. M2.3：让百科与平台资料在同一事实层可用

### 2.1 平台详情用可选能力，不替换旧方法

保留现有 `fetchArtistIntro` 的字符串返回合同。新增可选的 `fetchArtistMetadata`、`fetchAlbumMetadata`，优先消费新方法，缺少新方法时再包装实际存在的旧方法。`fetchAlbumTracks` 继续只负责曲目表。新方法未声明的平台仍可搜索、播放和使用旧人物页。

已实施的平台文字 DTO 包含供应商命名空间、实体类型与原生 ID、名称、带语言的正文／简述、出处、修订和使用范围；发行属性、图片和 credits 由当前实际支持的 MB／CAA／Commons 适配器分别提供。未来平台若提供这些字段，再增可选版本化能力，不要求所有平台补齐一份全能响应。Core 验证 ID、大小、方法能力和当前上下文后落库。

- 不支持、未提供、未找到和请求失败分别返回；空数组或空字符串不删除此前有效事实。
- 专辑详情区分专辑项目、平台专辑、具体发行，平台 albumId 不自动成为 MusicBrainz Release ID。
- 保留原始语言；旧纯字符串资料无法判断语言时为 und，按 M2.2 的候补规则展示。
- 介绍先选用户语言，再选该上下文可用的来源；本地共享正文同语言默认百科优先。平台原页自身资料仍按来源优先规则展示。
- 同步[方法白名单](D:/Project/Twilight_Echo/src/shared/mediaProviderMethods.ts)、[插件 SDK](D:/Project/Twilight_Echo/packages/plugin-api/src/index.ts)、宿主校验、RPC 与实际供应商实现；不让插件声明不存在的方法。
- 元数据请求沿用 Core 限流与取消，补齐插件内部 requestContext／AbortSignal 传递。查询不隐式登录，不增加旧播放或本地阅读的登录前提。

### 2.2 图片与文字分别判断权利和缓存

逐字段记录 `display / cache / crossSource / export` 使用能力和到期条件；API 可访问不代表四种用途均可用。未知使用条件的内容不自动复制到共享资料或备份。

- 本地内嵌／用户指定封面优先；已确认发行可取该发行 CAA 封面，只有项目时使用明确标为“项目封面”的回退。图片命中不确认发行。
- CAA 图片与 MB 核心结构数据分别处理；Commons 图片逐张保留作者、许可和署名链接。缺少所需权利信息时保留当前封面或占位。
- 受限平台图片只出现在获准的来源上下文。注销或禁用后停止新请求，按该范围处理缓存；不删除用户自有图片。
- 扩展[现有图片投影](D:/Project/Twilight_Echo/src/main/coreProcess/artworkProjection.ts)及媒体缓存：持久层保存受控资源记录，读取时重发会话句柄，不保存临时授权 token；公开 DTO 不含凭据、授权查询参数或本地路径。
- 文字按纯文本或受限格式渲染；外链走现有安全打开方式。图片大小、类型、重定向和远端访问沿用现有媒体安全策略，不另起任意 URL 下载器。

### 2.3 credits 的目标必须保留

每条关系保存 `personRef + role + targetKind + targetRef + order + attributes + attribution`。保留原始角色并映射规范角色；未知角色可显示原文，不折成 producer。

专辑制作关系挂发行／项目；歌曲录音、混音、演唱挂录音；词曲关系挂作品。M2 先保存类型化的外部作品引用和关系证据，M5 再物化完整作品／演绎导航，不为显示名单提前建设整套探索功能。只有来源曲目 ID 或 trackTitle 的历史关系先挂来源范围引用，缺少依据时不外推到其他同名歌曲。多人显示保留顺序和 joinphrase。M2 可展示基础名单，M5 才开放完整参与内容查询。

**完成证据**：无 MBID 的平台歌手能读取其获准资料；同一人物在本地与平台来源上下文可查询同一事实层；未确认发行不串精确封面；缺正文、图片或供应商不可用仍能播放；基础角色不丢失或改义。页面展示由 M2.5 消费这些结果。

## 3. M2.4：Rhine 切换期间只有一份可写资料

先从[当前 experience 生产入口](D:/Project/Twilight_Echo/src/core/plugins/experiences.ts)和[文档仓库](D:/Project/Twilight_Echo/src/core/plugins/experienceDocuments.ts)读取旧资料。旧 album ID 沿现有派生与 Track 成员映射，不通过标题重建；无原成员的资料进入未归属区。

1. 记录旧文档 revision、实际来源 ID、成员依据和待迁记录清单；使用现有一致备份保存主库，旧 JSON 与其备份作为恢复材料。
2. 分页暂存资料与映射。记录级结果为已归属、待确认、冲突或未归属；每条保留旧键和原载荷。`matched` 但无身份证据的旧记录不能直接成为共享已确认事实。
3. 保留 `external-ai` 导入正文的 method、references、batch、时间及人工注记；按用户导入资料展示，自动刷新不覆盖。旧 proofs、预览与 edition revision 校验继续生效。
4. 暂停该域写入并等待旧任务收尾，再核对源 revision；变化则重新预览，不提交旧快照。目标事实、映射及完成标记同 SQLite 事务发布。
5. 成功后切换旧 document／task／preview／import／reconcile 入口：资料读写使用主库，revision 冲突仍返回可重读结果，旧 JSON 不再写资料。失败时未发布新权威，旧入口继续可用。

旧文档包含非资料配置时，适配器按字段路由，不能让一次整文档替换把旧自动资料重新写回主库。尚未切换的流派规则仍由其原域管理；M2.4 不新增该字段的第二份可写分类。M3 在分类迁移时单独核对原始规则、别名与覆盖。

**完成证据**：旧入口修改一次即在主库资料查询中可见；重复启动不重导入；已有人工值、导入正文与未归属载荷可恢复；每条旧记录有处理结果，迁移成功数不能把待确认／未归属当成已确认身份。

**已实施部分**：schema 20、原 ID／成员映射、原载荷与 proofs、分页暂存和事务发布、导入备份、冲突／未归属清单、历史读取及带当前 revision 的恢复已落地。原人员只作来源范围引用，不升级共享身份。旧查询生产入口已接 Core 唯一持久 worker，批次提交、取消、重启和权限撤销已验证；旧页面生产验收仍待恢复环境。详见 [M2.4 记录](D:/Project/Twilight_Echo/docs/unified-music-library-m2.4.md)。

### 页面入口与状态

- 人物页共用资料组件，保留当前来源的歌曲列表；历史 `artist:名字` 无法唯一定位时先列可选人物，不把同名人的传记混入本地页。

### 内容与恢复验收

固定至少 200 条人工核对条目，本地、平台各至少 100 条；可在同一条目覆盖多个边界。热门与非热门中文、英文、简繁别名、同名异人、多人合作、多碟、CUE、部分专辑、现场／翻唱／重制、无有效标签均须有样例。记录来源快照或可复核依据，不用接口 200 代替正确身份。

分别报告人物、录音、项目、发行的确认量；介绍按语言、图片按层次、credits 按目标的覆盖量；错误关联和待复核量。每项给出分子、可适用分母、缺失／受策略限制／失败数；fixture 行为和真实服务抽样分开。固定样本自动错误关联为零。

恢复场景覆盖关闭窗口、Core／数据库 worker 重启、429／503、取消后的迟到结果、配置关闭、插件禁用、人工值保护与撤销。实际 Electron 页面检查键盘、窄窗口和主题下的人物页、专辑页与候选动作。M2 的完成条件仍是这一用户链路可用，不以接口已经存在代替界面验收。

## 5. M3：流派层级、分类维度与版本浏览

### 5.1 单父流派树，多值成员与可撤销映射

在现有 SQLite 增加流派、别名、原始分类证据、实体关联和覆盖。首版使用**单父树 + 递归 CTE**，不同时维护闭包表；只有实际性能证据要求时才替换投影。

- genre 使用稳定 ID、中英文显示名、可空 parentId 和字典版本。用户可增改；字典升级不重置用户父级和名称覆盖。删除有子节点／引用的流派需先选择迁移目标或转未映射，不级联丢数据。
- 内置字典自行维护，基础风格少而清楚；别名按来源和规范化规则映射。`Jazz / 爵士` 可同 ID，“华语”“粤语”“现场”“夜间”分别归地区／语言／属性／个人标签，不直接成为流派父节点。
- 保留本地原始 genre 字符串及用户分隔符，结构化平台数组不再按字符串分隔符重拆。旧 `genre` 精确筛选仍走旧含义；新 ID 与子流派查询走独立参数。
- 已知别名自动映射；未知值作为未映射项，用户可映射到已有流派、创建流派或忽略。忽略只抑制该映射建议，不删除原始字段。
- 人工指定流派集合／明确空集合 > 当前来源有效分类 > 当前上下文获准的外部分类。多值在同一层去重，后台事实不因改映射而丢失；reset 恢复自动合成。
- 多来源的实体查询使用其实际库内来源的有效流派并集，详情保留来源区别。专辑有直接分类时使用直接值，否则可用其库内曲目分类并集作“来自曲目”的回退；专辑流派不反向写每首歌。人物仅用于探索其参与内容，不把个人风格灌入所有作品。
- 改父级在同一事务检查完整祖先链、孤立引用和 revision；拒绝任意环。父流派计数按查询目标去重，不叠加子节点计数。

初始外部分类只启用已核实允许的字段。MusicBrainz 核心结构许可不自动覆盖其社区 genres／ratings；平台字符串也不自动获得跨源使用权。TheAudioDB、Last.fm 等仍为可选，分类能力不等待购买资料服务。

### 5.2 分类维度不混为评分

| 维度 | 保存与筛选规则 |
|---|---|
| 流派 | 稳定 ID、多值、可含子流派，未知不自动挂根节点 |
| 语言／地区 | 带出处的分类值，未知可筛；不因人名或平台地区猜歌曲演唱语言 |
| 年代 | 项目首次发行年与具体发行年分开；年份筛选显式选字段，不把再版年当首发年 |
| 专辑类型 | album／single／EP／compilation 等由允许来源映射，保留原始值与 unknown |
| 版本属性 | live／remaster／deluxe／clean／explicit 等独立多值事实及证据 |
| 技术规格 | 格式、位深、采样率等留在具体来源；未知不视为低规格，不换算成质量星级 |
| 管理状态 | 未识别、发行待确认、缺介绍、来源离线等可筛，区别于音乐风格 |

旧曲库“流派”入口改为 ID 分类投影时保留历史字符串导航适配：一个旧值映射多个节点就显示选择／组合结果，不取首项。Rhine 的 genreId、rawGenres、别名及 albumOverrides 按原 ID 和来历迁移；首曲流派派生值不冒充专辑人工覆盖。

### 5.3 专辑项目、发行、播放版本分开

专辑页按“项目 → 发行／本地待识别专辑 → 可播放来源”展开。默认展示当前版本，其他发行按需分页；未入库的外部发行清楚标为目录资料，不因查看就加入音乐库。

保留[现有版本模型](D:/Project/Twilight_Echo/src/shared/musicVersions.ts)的三层含义：同一播放版本可有多个来源，版本族可包含多个不同版本，资料中的具体发行另有身份。手工版本关系在原版本服务中修改，资料识别不反向重写它。

统一播放按以下顺序准备来源：

1. 解析当前目标及用户首选版本；从该播放版本的获准等价来源中选择用户首选来源，再用用户来源顺序、成员加入时间和稳定 ID 兜底。未明确等价时只尝试当前来源。
2. 从 Focus／集合发起时，候选来源还必须属于该次查询冻结的可用范围；“本地 24-bit”不能因来源偏好而改播云端或另一版本。
3. 在原播放安全／授权链路验证本地可访问、平台登录、地区限制和 URL 可用性。M1 的 indexed 状态不能跳过这一步。
4. 准备失败后只尝试同一播放版本内其余已确认等价来源，每次准备同一候选最多一次；全部失败保留具体原因和改选入口。不跨版本族，也不在族内悄悄切到另一母带／剪辑版本，不做播放中途无缝换源。

**明确点击来源继续走旧 `catalog.play(sourceId, revision)` 和原失败行为。** 新统一播放是独立操作，不能把旧调用改成自动替换。录音 ID／ISRC 相同、格式更高或都在某版本族里，都不足以单独证明可换源。

### 5.4 M3 的三次交付

- **M3.1 分类仓库与迁移**：树、别名、原始证据、覆盖、旧入口适配；样例验证重新扫描保留人工值，改映射可重算，任意环被拒绝。
- **M3.2 分类查询与页面**：分类维度、父子包含、未映射整理与分页计数；同一专辑命中多个子类只计一次，本地与平台筛选可用。
- **M3.3 版本页与统一选源**：发行关系、来源状态和两个播放入口贯通；现场／重制与精确发行不误合并，显式点击不改选，统一播放只在等价集合内回退。

**当前实施**：M3.1—M3.3 功能已接入。分类维度只采用现有可靠字段，语言／版本属性暂无权威字段时可筛未知并显示能力原因。schema 22 的资料修订及完整 token 约束列表、计数、来源和分面；平台专辑直接目标需真实非空原生专辑 ID，不按名称合并。原专辑页已接项目／物理发行／人工播放版本及音源，新 `catalog.playUnified` 在冻结范围内按原手工等价关系准备并一次提交；旧明确来源操作不变。目录成员首次实际发布时刻随成员事务持久化，移除重加保留首次，缺少旧历史时稳定 ID 兜底。细节及证据见 [M3.3 记录](D:/Project/Twilight_Echo/docs/unified-music-library-m3.3.md)及 [M3.2](D:/Project/Twilight_Echo/docs/unified-music-library-m3.2.md)。实际页面／内容验收仍按用户安排后置；M4.1—M4.3 评分、收藏／自动禁播及标签亦已接入，接续 M4.4 Focus。

## 6. M4：个人评分、收藏、禁播、标签与 Focus

### 6.1 歌曲与专辑有独立评分，不以项目评分代替发行评分

个人值按 `profileId + targetKind + stableEntityId` 存储，服务端校验 `1..10` 整数对应 `0.5..5` 星，NULL 为未评分；保留 updatedAt 与 revision。歌曲针对录音，专辑针对具体发行或稳定的本地待识别专辑，不能把歌曲所属专辑的分数显示成歌曲分。

确认跨来源身份后，同一录音共用歌曲个人分；现场／翻唱录音分开。专辑项目下不同发行不共享个人分，未确认发行的本地专辑先保留自己的值。

关联前检查已有个人值：相同可合并读取，不同则预览并要求用户选择。保留原目标与变更历史，不复制到所有发行。解除关联后，该来源恢复原范围记录；新写入共享目标的分数留在共享目标，不自动复制给被拆出的来源，预览说明影响。

### 6.2 外部评分保留机制、量程和适用层次

每条资料评分保存供应商、原生目标、评价类型（编辑／社区等）、rawValue、量程定义、票数、时间、出处和使用范围。热度、播放量、匹配分数、编辑精选均用独立字段。

- 项目评分只显示为“专辑项目资料评分”，不默认为每个发行的基础分，更不灌入歌曲分。查询需要项目评分时显式指定项目层次。
- 按供应商明示的规则换算五分制，例如 0—100 除以 20，1—5 保留原值；不能仅凭量程上下界推断换算，更不能平均不同供应商。
- 展示可保留小数；筛选比较未舍入值，不能让 3.96 因显示为 4.0 混入“四星以上”。个人半星步长不强加给外部分数。
- 没有合规可用来源时只提供个人评分和“暂无资料评分”。商业构建默认不启用尚未获准的社区评分字段。

默认同时显示“我的评分”和带来源名的资料分。`personal` 只读个人值；`base` 读取显式选择的供应商与目标层次；`effective` 在同一目标先个人、再所选资料源，未选资料源时等同 personal。清除个人分保留清除记录，恢复可用资料分，但仍属于“我未评分”。

**M4.1 已实施**：schema 23、个人值／清除／历史、物理目标选择、关联评分冲突及历史恢复、原歌曲／发行评分入口、外部评分纯函数和真实 Core／worker 接线已完成。人工播放版本仅导航，不能合并不同物理发行评分；真实资料评分源尚未启用。自动化证据及实际验收待办见 [M4.1 记录](D:/Project/Twilight_Echo/docs/unified-music-library-m4.1.md)。

### 6.3 收藏切换保持旧入口、顺序与跨来源含义

`none / favorite / ban` 按 Profile 与目标存储，保留清除时间和 revision；评分独立。M4 先支持录音、专辑及已确认主艺人的偏好，作品入口在 M5。

1. 仅按 `isDefault` 选出现有系统收藏，按原录音等价规则生成逐项映射；缺标记时新建独立系统列表，不接管普通同名歌单。无法确认的新身份保留来源范围引用，不比旧入口更激进地合并。
2. 暂存完整歌单文档、偏好及收藏视图的顺序、原 Track 快照和旧 ID。普通歌单的重复 occurrence 完全保留；默认收藏继续遵守原有去重规则。为偏好保留准确来源，不因此增加库成员。
3. 连续读取同一份完整、有版本的旧快照，以旧歌单 revision 核对，再将完整歌单文档、偏好权威和完成标记同 SQLite 事务发布，旧 `playback.favorite`、歌单收藏读写与批量入口转为适配器。原 CAS 及 20 MiB 上限保留；旧 JSON 只作恢复材料，不再业务写入。只迁默认成员而继续写完整 JSON 会形成跨存储双写，不能采用。
4. `favorite: false` 只取消喜欢，不清除已有 ban；取消禁播使用明确操作。取消本地喜欢不调用平台 unlike；原平台点赞按钮保持平台行为。

“我收藏的音乐”保留原系统歌单入口、名称、排序及快照，成员由偏好投影；普通同名歌单不被误吞。全量计数按迁移前对应的逻辑成员比较，同时列出原始行数、合并映射与待确认项，不用去重后的数量冒充无损逐行迁移。

自动推荐／心动使用统一的自动选曲判定：录音、所属选定发行或明确主艺人的 ban 均排除，专辑 ban 优先于曲目 favorite；作曲／混音等其他 credits 不传播人物禁播。初始推荐、后续 refill、Next／Previous、自然曲终及来源准备后提交音频前均检查；偏好变化不强停当前曲目。用户明确点播、具体队列选择或主动播放普通歌单及 liked 列表仍可播放，不重排已有队列。每次最多检查 100 个已有 occurrence、最多补充一次；私有批量判定每批最多 200 首，返回不完整则失败，不视为放行。

**M4.2 已实施**：schema 24、偏好值／清除／历史、完整歌单权威迁移、原收藏入口及 `preferences.targets/detail/history/set` 已接线。身份确认、替换和历史恢复中的评分与偏好分别预览、分别三选；自动冲突停复核，偏好转接、身份和审计同事务，解除后恢复原实体值。自动判定只沿当前有效关联，不从历史平台 ID 恢复已解除的身份。心动上下文按持久队列身份判定，跨源修复为本地后仍检查禁播。

为使曲间新设置的禁播在提交前生效，自动推荐使用**单曲 native window，由 Core 在曲终衔接，不再使用原 native 预播／gapless**；普通队列保持原预播与无缝播放。原 v1 歌单备份导出、预览和恢复已读取 SQLite 权威，恢复 ID 与数据同事务，结果未知时可幂等对账，不回写旧 JSON；完整 music 域便携备份仍由 M5.2 实施。实现、证据与验收边界见 [M4.2 记录](D:/Project/Twilight_Echo/docs/unified-music-library-m4.2.md)。

### 6.4 标签只存实体引用，普通歌单保留 occurrence

首版标签按 Profile 保存专辑／录音引用和 revision，暂不支持嵌套标签；M5 再纳入人物／作品。为专辑加标签不复制当前曲目，为单曲加标签也不标记它出现的全部专辑。集合播放时展开**实际库成员**并按录音去重，未来新增的该专辑库内曲目自然包含。

普通歌单仍是有序 occurrence，不改成去重集合。标签名、成员和保存查询分别编辑；移除来源不删除用户标签或评分，离线条目仍可管理。

**M4.3 已实施**：schema 25 保存精确物理录音／发行成员，确认／解除外部身份不搬迁引用，名称和成员分别 CAS，删除同时检查两类 revision。原详情关联准确目标，全部歌曲页另有不依赖实体的管理入口。播放按当前同类型已确认录音身份去重，仅展开实际库成员；明确首选、首次实际入库时间和稳定来源 ID 决定候选，不默认偏爱本地。完整标签／目录／内容／身份 token 核对分页和队列采用，Core 每批最多 100 首直接进入原隐藏 builder，取消或准备失败不替换旧队列，采用后冻结。新 seed 的明确来源标记禁止按名称恢复到集合外。公共页不传路径或 Track 快照，平台 URL 由原 Session 按需获取。原 v1 歌单备份不含标签，完整 music 备份仍归 M5.2。接口与证据见 [M4.3 记录](D:/Project/Twilight_Echo/docs/unified-music-library-m4.3.md)；真实桌面验收后置。

### 6.5 Focus 的一套语义用于页面、计数和播放

新增版本化查询 AST，首版支持录音／专辑（发行或稳定本地专辑），`scope=library` 为默认。外部目录仅查询已缓存目录，不借 Focus 发全网搜索；旧 LibraryQuery 的字段与含义不变。

```json
{
  "version": 1,
  "entity": "recording",
  "scope": "library",
  "where": {
    "all": [
      { "genre": { "id": "<jazz-stable-id>", "includeDescendants": true } },
      { "rating": { "target": "self", "mode": "personal", "gteStars": 4 } },
      { "notPlayedWithinDays": 90 },
      { "automaticPlaybackBlocked": false }
    ]
  },
  "sort": [{ "field": "personalRating", "direction": "desc" }]
}
```

此为待实现合同示例，genre ID 从分类查询取得；个人分转换成 steps 比较。查询由 Core 注入默认 Profile，不接受客户端伪造任意 profileId。保存查询每次打开动态求值。

语义固定如下：

- `all / any / not` 编译成参数化 SQL，字段白名单；深度最多 8、叶子最多 64、页大小最多 200。排序用稳定实体 ID 兜底，NULL 排后。
- 缺值不满足比较；`not` 是当前 scope 内的集合补集，因此“不是四星以上”包含未评分。另提供存在／缺失条件，UI 区分“低于四星”与“未评分”。
- 来源格式条件在**同一个来源行**上联合判断；“本地且 24-bit”不能由本地 MP3 加平台 24-bit 拼成命中。多个来源条件必须显式表达，返回匹配来源范围供播放使用。
- lastPlayed 使用现有 Core 统计定义，按已确认来源映射取最大时间；不按标题猜历史。最近 N 天按冻结 asOf 的 N×24 小时比较，含无记录；界面写“无播放记录”，不把被清理／压缩的历史缺失宣称为从未听过。
- 首版分面统计保留**全部当前条件**，显示“当前结果中的数量”；暂不做复杂布尔树的排除本维度重写。父流派、专辑及来源计数按目标实体 DISTINCT。
- 列表、总数、分面、播放物化共用一套编译器和 queryToken；token 包含查询版本、asOf、相关 catalog／分类／偏好／资料／历史 revision。变化则返回过期并刷新，不混用不同快照数字。
- 开始播放时以该 token 分批形成数据库内的选择／队列快照，再原子发布；取消保留旧队列，未知提交结果按请求 ID 对账，不重放播放命令。后续改评分或补资料不改变已发布队列。
- 只向窗口传当前页和汇总，不传全量命中 ID／DTO；不得先在 Renderer 拉完整曲库再做筛选。

## 7. M5：人物作品探索与可恢复的完整交付

### 7.1 人物与作品探索不靠同名串联

在 M2 credits 上增加按角色的分页参与查询，从歌曲打开演唱、作曲、作词、制作等人物，再看实际入库参与内容；外部目录单独标记。未确认人名仍可显示来源名单，不把所有同名 credits 聚合为同一人。

新增 work／performance 及有序录音关系时沿明确外部关系或人工确认。一个演绎可跨乐章，多次演绎分开；缺演绎实体时显示已有 work→recording 关系，不从曲名补出虚构的完整演出。人物／作品加入统一搜索、标签与偏好；星级范围仍是歌曲和专辑，不扩展成人物／作品打分。

### 7.2 新备份写 v2，仍读现有 v1

**选择新 envelope `twilight-personal-data` v2，新增可选 `music` 域（域内 version=1），新应用同时读取 v1／v2。** 当前 v1 白名单会拒绝未知域，不能继续标 v1 再偷偷加字段。旧应用仍使用 v1 备份；新版文件在旧应用中的不兼容须在导出界面说明，不能将它作为回滚文件。

music 域保存：

- 个人评分、favorite／ban／none 和清除记录，收藏视图排序与必要快照，标签及成员、保存查询；
- 人工资料覆盖／明确清空、手工图片的可导出资源、资料首选；
- 稳定实体及最小锚点、外部引用、确认／拒绝／解除与恢复所需关联历史、旧 ID 映射，以及人工演绎与有序录音关系；
- 用户流派节点、别名映射、层级覆盖与字典版本。内置字典可重建，用户修改不能靠可清缓存保存。

版本关系仍由原 `versions` 域导出，music 只保留其引用；v2 的旧系统收藏成员由 music 导出，`playlists` 不再提供第二份可恢复成员权威，保留系统视图身份及普通歌单。恢复界面按备份版本标明：v1 playlists 为“歌单与收藏”，v2 playlists 为“歌单”，v2 music 包含“收藏与音乐整理”；只恢复 v2 歌单不覆盖现有收藏偏好。自动 HTTP 缓存、运行中任务、受限全文／图片、凭据和会话 URL 默认不导出；用户自有图片采用受限大小的备份资源记录，不导出临时句柄。

新音乐域使用 180 MiB 总预算中的可用空间，设置明确记录／字节校验，不落入当前未知域默认 16 MiB 的处理。超限显式失败并允许用户选择导出域，不静默裁剪评分、关联或成员。主库一致快照仍可用于本机完整恢复，与便携个人备份分工不同。

**M5.2 功能已接线**：v2／music、选择导出域、引用与路径预览、个人值／清除／拒绝／解除、Rhine 人工正文和有序演绎，以及手工资料图片和逐实体资料源首选。schema 28 为用户图片保存每张不超过 2 MiB 的有界位图字节，music 使用剩余总预算并保留旧 music v1 读取。新人工正文保存逐字段来历，旧不明正文在设置页按当前／历史版本确认有权迁移或排除；未确认正文不导出。跨字典恢复保留本机内置定义和准确 ID，携带新增节点及所选用户修改，阻止未知别名标准化规则与合并环。实际内容、桌面和包内恢复仍在后置验收范围。实现及证据见 [M5.2 记录](D:/Project/Twilight_Echo/docs/unified-music-library-m5.2.md)。

### 7.3 恢复先验证引用，再按现有日志机制发布

1. 预览版本、各域数量、冲突、缺来源和路径映射。默认把备份默认 Profile 映射到当前默认 Profile，不因此建立多用户系统。
2. 对 library／versions／music 的相互引用给出依赖提示。只恢复 music 时保存最小实体锚点及离线／未绑定引用，不把未授权路径变为可播放来源，也不按同名歌猜绑定。
3. `keep-local / use-backup` 对每个稳定目标与字段作确定选择；确认／拒绝／解除及清空是实际状态，不通过删行“还原”。冲突涉及身份时先做映射预览，再应用个人值。
4. 记录输入 revision 与 restoreId，沿现有 redo／启动恢复流程暂存跨域数据；在启动、相关业务 owner 接受写入前执行恢复。同 SQLite 内容事务发布；跨存储使用日志与完成标记恢复，不宣称跨文件原子提交。暂存到重启之间允许正常使用，以 CAS 防止覆盖新数据；revision 已改变且 bundle 未提交时，保留完整备份转设置页待复核，不继续旧恢复请求。
5. 重启依次恢复权威、绑定已存在的来源，再重建目录／分类／历史查询投影；不导入旧 running 任务，也不因恢复文件擅自联网。完成前不接受冲突的新资料写入。

v1 恢复仍保留当前行为；旧默认收藏经新收藏适配器进入唯一偏好权威。缺少或未选择 music 域不清空已有评分、标签和资料覆盖。恢复后仅按明确来源映射接回曲目，失联资料保留可管理状态。回滚到旧版本使用切换前的匹配快照；已有新个人数据先导出 v2 保存，不让旧二进制直接打开新 schema。

## 8. 公共接口与验证如何落到现有工程

下面是操作组与合同，不提前建立未使用 API。每一阶段在实施时同步 DTO、权限、校验、数据库 worker、Core application／生产入口、桥接／客户端及实际调用者。

| 阶段 | 增量操作组 | 必须保持的旧含义 |
|---|---|---|
| M2.3—M2.6 | 资料能力／详情／覆盖；可选平台详情；任务与复核投影 | Track 补全、平台字符串 intro、Rhine 导入预览、原文件问题 |
| M3 | genre tree／aliases／mapping／override；分类分页；发行列表；unified play | genre 字符串筛选、手工版本服务、显式 source play |
| M4 | rating／preference；tag／members；saved query／Focus query／facets／play／play status | 旧收藏入口、普通歌单 occurrence、平台点赞、已有播放队列 |
| M5 | credits participation／work relations；备份 v2 预览／恢复 | v1 读取、版本域、来源授权及现有 redo 恢复 |

新增读操作沿 `library:read`、库资料及个人整理写操作沿 `library:write`；播放仍需 `playback:write`，备份仍经现有备份权限与用户文件选择。旧操作保留原载荷和权限，例如 `playback.favorite` 仍按原 `playback:write` 经 Core 适配，不新增 library:write、平台登录或外部资料启用前提。手动刷新／补全需写权限，网页／插件不能靠查询接口写外部事实或抓任意 URL。资料网络能力、账号能力和本地库操作分别判断。

公共分页默认有界，候选、关系与正文另设条数／字节上限；私有文件路径与授权 URL 留在原受控通道。字段写入采用相关 revision，事件仅携带受影响 ID 和修订；查询 token 包含相关依赖，外部资料更新不重建当前播放队列。

验证随交付复用现有实体／目录数据库、Core／插件、收藏／版本／听歌统计、备份及 Renderer 用例；原生运行依赖现有 `test:core:electron`，包内依赖 `test:core:packaged` 和实际 Windows gate。真实服务只做获准且限流内的抽样，故障／大样本／性能使用可复现 fixtures。
