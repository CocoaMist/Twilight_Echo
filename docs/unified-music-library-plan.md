## 1. 已确定的产品决策

| 项目 | 实施决定 |
|---|---|
| 运行方式 | 本地 Core 管理身份、资料、查询和任务；桌面端直连已启用资料源，不建设共享云目录 |
| 发布方向 | 保留商业发布能力；数据许可、API 服务条款、图片和文字授权分开处理 |
| 主入口 | 统一音乐库，支持全部／本地／各平台筛选；保留文件夹及平台发现入口 |
| 自动补全 | 可靠结果补缺失字段，手工编辑和已有有效标签优先；可查看来源、纠正和撤销 |
| 评分 | 专辑、歌曲分别支持半星至五星；未评分为空；个人分与资料分分开 |
| 来源选择 | 尊重明确点击；统一曲目支持等价来源选择，不把本地或流媒体设为永久高优先级 |
| 文件保护 | 补资料不回写音频、CUE 或平台账号；已有显式标签写入、平台点赞入口保持原用途 |
| 用户范围 | 首版使用一个默认 Profile，数据以 profile_id 分区；本轮不建设多用户登录与共享服务 |
| 交付边界 | 完成 M1—M5 才是本方案交付；M2 是第一个可体验的补资料里程碑 |

## 2. 稳定身份、资料与个人状态的统一模型

### 2.1 实体关系与存储位置

```text
人物／团体 ──角色──> 作品、演绎、录音、发行
作品 ──> 演绎 ──> 录音
专辑项目 ──> 发行版本 ──> 碟片／发行曲目 ──> 录音
录音／播放版本 ──> 来源：本地文件、CUE 片段、平台项目
Profile ──> 评分、喜欢／禁播、标签、首选版本／来源
```

- 新增资料实体、关系、事实、个人偏好和查询索引放在**现有音乐库 SQLite**，由数据库服务提供有界操作，Core 决定业务行为。查询所需表位于同一连接，避免跨数据库关联和假原子事务。
- 现有 core-state、版本和歌单存储在各自切换前仍是原域权威；完成迁移后，相应旧接口转为新仓库适配器，不能双写两个权威。
- 使用内部稳定 ID，不用标题、人名或外部供应商 ID 直接作全局主键。外部 ID 以供应商、实体类型和 ID 类型限定命名空间。
- MusicBrainz 不是入库或获取资料的前提；平台原生人物可直接定位，确认与本地人物的关联后，分别读取允许跨来源使用的百科或平台资料。
- 给旧 Track、来源键和专辑组建立映射，保留原 ID 与队列身份。没有外部资料的本地条目也有实体；元数据改名不会重建它。
- 文件搬移只在扫描／文件操作提供明确映射时转接来源身份；否则保留旧的离线来源供用户修复，不凭同名文件猜迁移。
- 作品、演绎和录音的关联允许多条及顺序；资料没有提供演绎信息时不虚构演出实体。

新增表按五组组织：

| 表组 | 必要内容 |
|---|---|
| 身份与关系 | entity、external_id、artist、album_project、release、release_track、recording、work、performance、credit；旧 ID 映射及身份关联依据 |
| 来源与成员 | source、source_binding、library_membership、版本与等价来源关系；来源类型、原键、可用性、最后可用时间 |
| 资料 | fact、attribution、field_override、match_candidate、metadata_job；目标层次、语言、许可、时间及修订号 |
| 分类 | genre、genre_alias、entity_genre、tag、tag_member、saved_query |
| 个人状态 | profile_preference、profile_rating、source_preference；明确状态、更新时间和 revision |

表随对应里程碑增加，不一次建空壳。保留现有 files/tracks、FTS 与持久队列表。

### 2.2 身份关联不等于允许换源

- 本地与平台可能是同一录音，但母带、剪辑、显式／洁净版本不同；分别保存“录音身份”和“可互换播放版本”。ISRC 或录音 ID 相同也不能独自证明母带一致。
- 标题、歌手、时长相似用于召回候选，不能单凭这些信息持久合并。自动确认需要唯一且一致的 ID／关系证据，或唯一整专辑候选与逐轨对齐；冲突、版本词矛盾及多个有效候选进入复核。
- 歌手、录音、专辑项目、具体发行分别确认。只确认歌手或专辑项目时，就先补该层的介绍和分类，不要求具体发行也成功。
- 对来源的确认关联必须可撤销，保留原始实体和关联历史；不因自动匹配物理删除旧实体。用户明确拆分的关系不能在下次后台查询中复合。
- 合并前预览受影响的评分、收藏和标签；存在冲突个人值时不静默覆盖，要求选择保留值。自动任务不处理这种冲突。

### 2.3 资料合成规则

展示优先级：**手工指定／明确清空 → 来源自身有效标签 → 已确认、允许使用的外部事实 → 文件名等现有兜底**。自动刷新只替换自己的缓存事实，不抢写用户值。

- 将首次发行日期和具体发行日期分开，保留日期精度。录音识别成功不会把它出现在目录中的某一张专辑写成文件的原发行。
- 简介按简体中文、繁体中文、英文回退，保留实际语言和出处。缺正文时只展示有出处的结构化资料概览，不生成无出处传记或乐评。
- 对获准的本地共享介绍，同语言默认百科优先、平台补充，也可手工指定；一次展示一份有出处的正文，不拼接。平台原页自身资料仍按来源上下文使用，身份确认不自动开放跨源权限。
- 图片记录原页面、作者及许可；具体发行封面和专辑项目封面回退分别标识。图片或文字不允许跨来源使用时，只在允许的来源上下文展示。
- 资料缓存和个人信息分别管理；来源要求过期删除内容时，保留允许保留的身份映射及用户评价，不删除整个实体。

### 2.4 入库和播放契约

- 本地导入、手动加入和用户明确启用同步的流媒体收藏属于音乐库；搜索／浏览结果仅进入目录缓存。默认不自动导入账号的全部历史或整个平台目录。
- 平台收藏同步首版是读取其成员并记录来源，不自动制造 Twilight 星级，也不把取消平台点赞解释为删除本地副本。
- 新增统一曲目播放：用户首选来源／版本优先，再按用户设置的来源顺序选择；未设置时用成员加入时间、稳定 ID 兜底。失效后仅在确认等价的来源中回退并显示实际来源。
- 用户明确点某个来源，以及既有版本管理中的显式首选播放，保持原有失败提示和改选行为；不自动改播另一录音。统一播放只在选定播放版本内已确认等价的来源中回退，不因同属版本族切换母带／剪辑版本，不做播放中途无缝切换。从筛选结果播放还需遵守当次匹配的来源范围。
- 来源列表显示本地离线、未登录、地区限制和平台下架等实际状态；授权 URL、凭据和本地访问能力继续由原播放安全链路管理。

## 3. 补全服务与客户端接口

### 资料源按能力接入

1. **现有流媒体适配器**：读取平台人物、专辑、曲目及可提供的介绍；身份先限定在该平台，再按明确关系连接其他资料源。
2. **MusicBrainz**：身份、发行和 credits；扩展现有适配器，不再只筛 producer。保存 Artist／Recording／Work／Release Track ID。
3. **Wikidata／Wikipedia／Commons**：已确认人物或专辑的多语言资料和可追溯图片。优先沿 ID 与 sitelink 查询，不只按名称猜页面。
4. **Cover Art Archive**：按确认的 release 或 release-group 查封面，回退层次可见。
5. **可选资料源**：Discogs、TheAudioDB、Last.fm 和在线指纹服务通过同一适配协议接入；首轮不把这些服务的 key、预算或商业授权设为基础功能前提。

每个适配器声明支持的实体、字段、端点、限流和缓存／展示限制。开发调试与商业发布使用不同部署配置；后者仅启用满足相应接入条件的字段和端点。MusicBrainz 核心结构与社区流派、评分的许可分别处理。商业许可确认属于实际发布依赖，不阻塞本地模型和适配器开发。

### 持久任务与取消

- 优先级：当前详情／手动任务 → 新增入库实体 → 历史回填。按“实体、供应商、语言、资料类型”去重。
- 扫描先提交本地记录，之后排队；重连窗口只订阅任务，不重建全库任务。
- 数据库保存待运行、运行中、等待重试、待确认、已完成、已取消状态；重启后将未完成运行重新排队。
- 按 host 共用限流，尊重 Retry-After；未找到、歧义、429／503 和鉴权失败分别记录，不把暂时故障当永久无资料。
- 使用 AbortSignal 和任务 generation；提交时再校验实体、来源版本与任务状态。取消后迟到结果不能发布；一个任务取消不影响共享请求的其他消费者。
- 读取不等待补全。补全提交后按受影响实体失效详情、搜索、分面和智能集合缓存，不重建当前队列。
- 网络设置说明将发送的名称、ID 和必要时长；不上传原始音频、路径、完整曲库或历史。指纹联网识别单独启用，不能把文件自带的未知指纹当声学证据。

### Core 公共接口增量

在 [coreProtocol.ts](D:/Project/Twilight_Echo/src/shared/coreProtocol.ts)增加有限查询／命令，并同步请求校验、权限、主进程桥、预加载、客户端和测试。只开放白名单领域操作，由 Core 校验插件提交的候选资料。

| 接口组 | 查询与命令 |
|---|---|
| catalog | entity/detail、relations、sources、query、facets；按实体加入／移出音乐库、确认关联、拆分关联 |
| metadata | entities 的补全、候选分页、确认／拒绝、任务状态／取消、字段覆盖／恢复 |
| preferences | 评分、喜欢／禁播、首选版本／来源；旧收藏入口使用同一仓库 |
| classification | 流派及别名、标签成员、保存查询的读取和修订 |
| MetadataProvider | 候选检索、实体详情、关系资料读取、能力和使用约束；支持取消信号 |

共享 DTO 包含实体引用、出处、分层识别状态、个人状态、分页与 revision。事件只传变更 ID／修订号和必要状态，不广播全库。现有 `metadata.start/apply/clear` 保留原本的本地歌曲含义，通过适配层接入；新实体补全使用独立有界命令。

## 5. 迁移、回滚与验证安排

### 切换规则

- 每个域切换前使用现有 WAL 一致备份机制；schema 版本按实施时最新值递增，不占用预设版本号。
- 旧数据通过固定 revision 分页读入 staging；在 Core 暂停该域写入的短提交阶段核对 revision，原子发布新域及完成标记，再将旧入口改接新仓库。中途失败继续旧读取或恢复 staging，不双写。
- 跨存储导入先形成可验证的目标快照，完成标记写入目标 SQLite 事务；原始 SQLite／JSON 数据保留为只读恢复材料，切换后不再参与业务写入。
- 记录迁移来源、映射和未解决项目；重启不会再次导入覆盖新数据。备份恢复走原有 redo／恢复机制，未知结果先读取核对，不重复播放或重放写操作。
- 运行时回滚以恢复匹配版本的备份为准；已有新个人数据时先导出，不用旧二进制直接打开更高版本数据库。

### 验证分工与必测场景

| 层次 | 必要证据 |
|---|---|
| 模型与数据库 | 引用、分页、唯一性、revision、迁移幂等／断点／回滚、合并冲突及拆分可恢复 |

| 查询与播放 | 库内／目录边界、不同评分语义、父流派去重、动态集合与队列快照、明确来源不改选、等价来源回退 |
| 个人数据 | 评分清除、取消收藏、重扫保留覆盖、平台点赞隔离、备份恢复、来源丢失时偏好仍在 |

商业发布时由发布负责人核对实际启用来源的服务与字段使用条件；不符合条件的来源关闭并标记不可用，不改用抓取或其他端点绕过。同类资料仍可由其他已启用来源补充。发布依赖不等于要求开发阶段购买服务。
